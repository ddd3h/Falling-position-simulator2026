## C-01：実行環境と最短の確認

既存CLIの受入環境はPython 3.12.12である。ソース構文の下限と数値依存の対応Pythonは別で、別環境では採用するSciPy/NumPyの条件も満たす必要がある。保存された気象場の`inspect`は標準ライブラリ、`simulate`はSciPyとNumPy、`fetch`と`replay`はGRIB復号のecCodesとNumPyを必要とする。依存不足を本体が自動インストールすることはない。

このWindows環境では、取得・復号・飛行に既存の`C:/Miniforge3/python.exe`を使う。0.24の数値受入はSciPy 1.17.1 / NumPy 2.4.4で行った。別の環境を使う場合も実際のPython・SciPy・NumPy・ecCodesの版を記録する。画面用環境はC-09のlockから構築し、ecCodes 2.48.0・GeographicLib 2.1に加えて、0.49の保存風統計用にDuckDB 1.5.5を含む。下のPowerShell変数は既存CLIの後続例で共通に使い、永続PATHや既存環境を変更しない。

```powershell

& $taskPython --version
& $taskPython -B -m balloon_sim --help
```

## C-03：固定例の飛行を実行する

最初は設定を書き換えず、同じ例が全工程を通ることを確認する。次の二例は上昇則が異なるが、同じ取得run・時刻系・気象照会・積分・保存経路を使う。

```powershell
& $taskPython -B -m balloon_sim simulate examples/hokkaido-simple.json --weather references/flight_fixture/hokkaido-weather.json.gz --output (Join-Path $taskOutputRoot 'hokkaido-simple')
$LASTEXITCODE
& $taskPython -B -m balloon_sim simulate examples/wakayama-isothermal.json --weather references/flight_fixture/wakayama-weather.json.gz --output (Join-Path $taskOutputRoot 'wakayama-isothermal')
$LASTEXITCODE
```

期待する終端は終了0、stdoutの`status: "landed"`、`complete: true`である。`result.json`の`events`に`burst`と`landing`があり、最大高度30000 m、最後の`height_agl_m`が0付近となる。ここでの着地は粗いGFS地形との交差である。

各例の`report.html`をブラウザーで開くと、水平軌道、高度と地形、時刻スライダー、設定と来歴を見られる。例としてPowerShellでは次を使える。

```powershell
Invoke-Item -LiteralPath (Join-Path $taskOutputRoot 'hokkaido-simple\report.html')
```

水平図は背景地図なしの局所投影である。地物の確認用の地図としては扱わず、別のGISへ渡す場合は`trajectory.geojson`を使う。GeoJSONの座標順は経度・緯度・高度である。

### 保存されるものと、最初に読む値

| ファイル | 内容・再現上の役割 |
|---|---|
| `input.json` | 渡した設定ファイルの元バイト。既定値展開前の入力を保持 |
| `result.json` | 採用設定、状態、記録点、イベント、停止理由、仮定、`numerics`（方法・依存版・許容誤差）を含む計算結果 |
| `provenance.json` | 元設定・保存気象のパスとSHA-256、気象メタデータ、パッケージ版、本体の下位パッケージも再帰した全`.py`の相対パスとSHA-256、数値法・依存版・設定 |
| `trajectory.csv` | UTF-8 BOM付きの軌道表。複合値はJSON文字列で記録 |
| `trajectory.geojson` | 軌道LineStringとイベントPoint |
| `report.html` | 通信を使わない図と時刻別状態表示。上の結果を読むための表示 |
| `manifest.json` | 他の成果物のバイト数・SHA-256、結果の完了状態。自分自身はハッシュ対象外 |

まず`status`・`complete`・`stop_reason`、次にイベントと最終地上高、最後に時刻範囲と品質フラグを読む。`landed`は「この入力と仮定で接地まで解けた」という判定であり、着地位置の予測精度や実機の係数の採用判断とは分ける。

### 終了コードを区別する

| 終了 | 意味 | 次の処理 |
|---|---|---|
| `0` | 取得・検査・再生の成功、または飛行が`landed` | 各出力と来歴を確認する |
| `2`、stdoutに`stopped`結果 | 計算途中の支持不足・物理拒否・時間/歩数上限等。部分結果を保存済み | `stop_reason`と最後の支持範囲を読み、変更条件を決める |
| `1`、stderrに`status: "error"` | 計算前入力拒否、既存出力、環境、取得、保存等のエラー | `code`と`message`を読む。計算済みだと扱わない |
| `2`、usageと引数エラー | argparseによるコマンド指定の誤り。飛行の`stopped`とは別 | 必須引数を修正し、結果ディレクトリの有無だけで成功を判定しない |

取得や保存の途中で失敗すれば部分ファイルが残ることがある。ディレクトリの存在だけで完了とはしない。既存出力の上書きは拒否されるため、原記録を保ったまま新しい出力名で再実行する。

## C-04：別の時刻・地域のGFSを取得する

### 要求と打上げ時刻は別の設定である

予報runは00/06/12/18 UTCで指定し、`run_utc <= start_utc <= end_utc <= run_utc + 384時間`を要求する。予報の最大384時間はrun起点であり、任意の打上げからさらに16日先まで取得できるという意味ではない。飛行が続く時間もこの支持範囲に含める。

時刻には`Z`または`+00:00`を明記する。JSTを表す`+09:00`やタイムゾーンなしの文字列は、このAPIでは自動変換せず拒否する。たとえば2026-09-23 12:30 JSTを使うなら、入力は2026-09-23 03:30 UTCとする。

0～120時間先は1時間刻み、その後は123,126,…,384時間先の配布時刻を使う。本体は要求区間を挟む最小の配信時刻を選ぶので、打上げを配布時刻に合わせる必要はない。固定例の03:30 UTCは03時と04時の場の間にある。単一run内で同じ高度の場を時間補間し、途中で新しいrunへ自動更新しない。

全国での利用は地域名の選択ではなく、`bounds`と飛行設定の座標を変える。範囲には予想される移流先まで余裕を含める。取得矩形は0.25度へ外向きに丸めるが、日付変更線等の経度継ぎ目をまたぐ要求は本版の一回取得では扱わない。

### 要求JSONと実行

[固定取得例](../examples/gfs-japan-request.json)の実体は次の値である。**これは旧取得の記録で、0.47のメモリ受入上限では大きすぎるため、そのまま新規取得するコマンドには使わない。**これは取得成功時の再現用の例であり、配布期間を過ぎた後までこのrunがNOMADSに残ることは保証しない。後日の新規取得では別ファイルへ、実際に公開されているrunと必要な期間を明示して作る。

```json
{
  "run_utc": "2026-09-22T18:00:00+00:00",
  "start_utc": "2026-09-23T03:30:00+00:00",
  "end_utc": "2026-09-23T09:00:00+00:00",
  "bounds": {"west": 130.0, "east": 151.0, "south": 30.0, "north": 46.0},
  "max_bytes": 50000000
}
```

```powershell
# my-gfs-request.json に、現配布run・必要時刻と飛行に必要な小領域を明示する
& $taskPython -B -m balloon_sim fetch my-gfs-request.json --output (Join-Path $taskOutputRoot 'gfs-acquisition')
$LASTEXITCODE
```

`max_bytes`は一要求の合計取得上限で、1024～50000000 bytesを許す。省略時も50000000である。上限内に収まらなければ範囲・期間の設計を見直す。0.47では復号作業メモリの概算が512 MiBを超える要求も通信前に拒否する。画面の取得計画では実行前に概算を読める。概算はRSS保証ではない。失敗時に全地球・別run・別URLを自動的に試す仕組みはない。

成功時は`request.json`、`decoder.json`、`fNNN.grib2`群、`provenance.json`、`weather.json.gz`、`receipt.json`が保存される。全圧力面の風・温度・高度・比湿と地上量を復号し、各列で幾何高度30 kmを支えることを確認してから保存場を作る。HTTP成功だけでは取得受入にならない。

取得開始後の失敗は`failure.json`と途中までのrawを残す。要求・依存・メモリ上限・既存出力等の事前拒否では取得ディレクトリを作らずstderrへ理由を返す。提供側の未配布、保存期限、欠測、単位、格子、上限超過を区別し、元の要求と結果を指示書へ記す。CLIの通信再試行は新しい出力ディレクトリへ行う。画面の明示再試行は保存要求・復号器・完了rawの照合により同じ仕事から再開する。raw入力の上限には、新規取得・再利用・保全した部分rawを含める。新規通信bytesとは区別する。NOMADSの索引/GRIB取得は同じOSユーザーで間隔を共有し、直前の完了から10秒以上を空ける。待機を未応答や停止と取り違えず、進捗と取消状態を読む。runを変えるなら新しい予報比較であり、元の同一入力再現とは区別する。

### 独自の飛行設定を作る

設定の全例は[北海道・指定上昇率](../examples/hokkaido-simple.json)と[和歌山・等温浮力](../examples/wakayama-isothermal.json)を参照する。変更はコピーしたJSONへ行い、元例と比較できるようにする。

| 部分 | 選択と必須入力 | 単位・組合せ |
|---|---|---|
| `launch` | `time_utc`, `latitude_deg`, `longitude_deg`, `altitude_m` | UTC、degree、海面基準のモデル幾何高度m。地上高を直接渡す欄ではない |
| `ascent` | `mode: "constant_speed"`, `speed_m_s` | 正の上昇速度m/s |
| `ascent` | `mode: "isothermal_buoyancy"`, `gas_mass_kg`, `envelope_mass_kg`, `payload_mass_kg`, `drag_coefficient` | 質量kg、Cd無次元。任意`gas_constant_j_kg_k`の既定値2077.1 J/(kg K) |
| `burst` | `mode: "altitude"`, `altitude_m` | 打上げ高度より高い海面基準m |
| `burst` | `mode: "diameter"`, `diameter_m` | 正の直径m。等温浮力上昇が必要 |
| `descent` | `mode: "constant_cda"`, `mass_kg`, `drag_area_m2` | 正の降下質量kg、Cdを含む有効抗力面積m² |
| `descent` | `mode: "rated_speed"`, `reference_speed_m_s`, `density_model: "weather"` | 正の基準降下率m/s。任意`reference_density_kg_m3`は既定値1.225 kg/m³ |
| `descent` | `mode: "rated_speed"`, `reference_speed_m_s`, `density_model: "exponential"` | 正の海面基準降下率m/s。任意`scale_height_m`は既定値8400 m |
| `integration` | `max_step_s`, `max_duration_s`, `event_tolerance_s`, `max_steps` | 任意。採用間隔上限10 s、時間上限14400 s、時間根xtol 0.001 s、採用上限200000歩が既定 |
| `integration` | `relative_tolerance` | 任意、既定1e-9。100×double epsilon未満は拒否 |
| `integration.absolute_tolerance` | `latitude_deg`, `longitude_deg`, `altitude_m` | 任意。正の有限値。既定は経緯度各1e-9 degree、高度1e-3 m |

数値積分はSciPy RK45の適応刻みで、結果の記録点は不等間隔になる。固定出力間隔への再標本化は未実装である。破裂では同時刻の上昇/下降2行があり、相とイベントで読む。`numerics.record_sampling`と、比較する各行の時刻を確認する。

モデル内の未知キー・未実装modeは拒否する。`gas_mass_kg`等を真偽値や文字列として渡さず、JSONの有限な数値で指定する。`density_model`省略時は`weather`である。`constant_cda`の値と`rated_speed`の値を同じ選択へ混在させない。

固定例の打上げ高度は、選んだGFS地形の5 m上に置いた数値例である。別地点へ緯度経度だけ移した場合、その高度は再利用できない。打上げが地表下なら`LAUNCH_BELOW_GROUND`となるため、場の地形を確認し、どの高度基準を採ったかを記録する。粗いモデル地形と実測標高の差を、黙って設定値の修正で吸収しない。

上の取得出力を使う際のコマンドは、設定ファイルを明示して次の形になる。`my-flight.json`は利用者が作った新しい設定ファイルである。

```powershell
& $taskPython -B -m balloon_sim simulate my-flight.json --weather (Join-Path $taskOutputRoot 'gfs-acquisition\weather.json.gz') --output (Join-Path $taskOutputRoot 'my-flight')
$LASTEXITCODE
```

気象の領域・時間外、地上から最初の有効圧力面への橋渡し、寄与格子の地形延長が結果をどう制限するかは、気象品質と理論ガイドで確認する。必要量がないときに比湿0や標準大気へ暗黙に代替することはない。

## C-05：取得済みrawを照合し、通信なしで再復号する

```powershell
& $taskPython -B -m balloon_sim replay (Join-Path $taskOutputRoot 'gfs-acquisition') --output (Join-Path $taskOutputRoot 'weather-replayed.json.gz')
$LASTEXITCODE
```

終了0で`weather_replayed`が表示される。保存した要求、lead集合、URL、ファイル名、バイト数、SHA-256を確認してからecCodesで再復号する。rawが欠けている、変わっている、来歴と一致しない場合は止まり、ネットワークで不足分を補わない。

同じ復号コード・依存版を使った場合、元の`receipt.json`の`bundle_sha256`と新しいファイルのハッシュを比較する。PowerShellでの読取例は次のとおりである。

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath (Join-Path $taskOutputRoot 'weather-replayed.json.gz')
Get-Content -LiteralPath (Join-Path $taskOutputRoot 'gfs-acquisition\receipt.json')
```

別版のecCodes等を使えばメタデータも変わるため、ハッシュ不一致を直ちに物理量の不一致とも、問題なしとも決めない。版・正規化した数値・スキーマの差を確認して記録する。

保存気象からの飛行再現では、`input.json`の元設定、元の気象ファイル、同じ本体コード・SciPy/NumPy版・数値設定を使い、新しい出力先へ`simulate`する。`result.json`の同一バイトは再現確認になるが、`provenance.json`には入力の絶対パスが入るので、別の配置の全フォルダー同一バイトまでは期待しない。

## C-07：TeXから必要なガイドを生成する

`THEORY_GUIDE.tex`と`PROGRAM_GUIDE.tex`は直接編集する原本である。計画書の`PROJECT_PLAN.md → tools/build_docs.py`とは生成経路が異なる。初版は既存専用XeLaTeX、Noto Sans CJK JP / Noto Sans Mono CJK JPと、検索テキスト抽出用のpypdfを使う。詳細な既存環境とフォントの照合は[BUILD](BUILD.md)を参照する。

この環境ではpypdfはbundled Python側にあり、Miniforge側へ新しく導入しない。次はprocess内の環境変数を元へ戻す生成例である。

```powershell
$taskDocsRuntime = 'C:\Users\genia\.local\share\balloon-docs'
$taskDocPython = 'C:\Users\genia\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
$taskGuideOut = Join-Path $env:TEMP ('balloon-guides-' + [guid]::NewGuid().ToString('N'))
$taskOldPath = $env:PATH
$taskOldFontConfig = $env:FONTCONFIG_FILE
try {
    $env:PATH = (Join-Path $taskDocsRuntime 'TinyTeX\bin\windows') + ';' + $taskOldPath
    $env:FONTCONFIG_FILE = Join-Path $taskDocsRuntime 'fonts.conf'
    & $taskDocPython -B tools/build_guides.py . --output-dir $taskGuideOut
    if ($LASTEXITCODE -ne 0) { throw 'ガイド生成が失敗。外側ログを確認する。' }
} finally {
    $env:PATH = $taskOldPath
    $env:FONTCONFIG_FILE = $taskOldFontConfig
}
```

生成器は新規出力先だけを受け入れ、各TeXを3回コンパイルして相互参照を解決する。PDFと検索用txt、各passのログ、入力・出力ハッシュを含む`build.json`を保存する。検索用txtはpypdfによる抽出であり、文字が得られたことと数式の正しい表示は別である。

終了0を確認した後も、既存`pdftoppm`等で全ページを描画し、文字欠け・数式・表・見出し・改ページ・リンクを確認する。表示を修正したらTeXへ戻し、新しい外側出力先で再生成する。PDFだけを手直ししない。

指定なしでは両冊を生成する。一冊だけ変更した場合は `--guide PROGRAM_GUIDE` または `--guide THEORY_GUIDE` を付ける（繰返し指定可）。選択したPDF/txtをrepoへ反映する操作は、同じコマンドへ`--publish`を付ける。この場合も新しい`--output-dir`を使い、生成器は選択した全冊のビルド成功後に、そのPDF/txtだけを`docs/`へ複写する。`build.json`の`selected_guides`を確認する。未選択の既存ガイドは再生成しない。版・元TeX・表示確認が一致した組を保存し、生成物だけ先に公開しない。

## C-08：途中停止から次の判断につなぐ

| 観測 | 原因の確認先 | 次に変える対象 |
|---|---|---|
| 時刻の支持を失った | `stop_reason`、runと有効時刻、飛行時間 | 取得期間。runの最終予報時刻を超えるなら打上げ/利用runの条件を再検討 |
| 緯度・経度の支持を失った | 最終採用点と取得矩形 | 領域と取得量。地域名の特例コードは足さない |
| `LAUNCH_BELOW_GROUND` / `BELOW_GROUND`、地形衝突 | 打上げ高度基準、局所地形、相 | 入力高度と地形の意味。衝突を着地成功へ変換しない |
| `INSUFFICIENT_LIFT` | 等温モデルのガス・膜・搭載質量と密度 | 物理入力・仮定。指定上昇率へ自動切替しない |
| 必要量欠測・GRIB識別不一致 | raw、要求、取得来歴、フィールド名・単位 | 取得/正規化契約。類似量への無記録な代替はしない |
| `MAX_DURATION` / `MAX_STEPS` | `integration`と最後の相・高度 | 必要な計算上限と異常の有無。上限だけ無条件に増やさない |
| `OUTPUT_EXISTS`等 | 指定したファイル/ディレクトリ | 新しい出力名。旧成果物を消して再利用しない |

停止理由を読んだ後、変更した入力、採用/保留の理由、再実行の条件と結果を同じ指示書の実施欄へ戻す。気象APIやモデル仕様の新しい知見は担当ガイドへ集め、手順書だけに長文の仕様を埋めない。この対応が、会話なしで次の計算と判断を再開するための記録になる。

## C-09：同じ計画で画面を使い、計算・保存・再開する

0.55は、以下の予報操作に受付の復旧と原日時比較を加える。0.54で接続した経路は、現在の配布を観測して選び、必要な予報を取得し、放球地点のモデル地表を確認して、以下の既存比較・保存経路へ進む。通信が途切れた場合も草案と固定結果を保持して状態を再確認する。0.53で加えたC-11と同じ保存JRA一窓の代表手順、0.49時点の到達範囲は以下へ残す。

0.49の開発中の画面は、既存の打上げ計画・詳細・気象分析・季節計画を共通の入口へつなぐ。0.47で加えた実予報の準備と明示適用に続き、固定GFSでのn=1と、一変量の仮幅から作る集合を選べる。集合は一つの固定気象に対する機体条件の感度であり、校正済みの気象誤差や過去場の統計ではない。実風統計は、提供されたJRA-3Qの半月集計DBを基に、年間・地域・季節分布を読む。0.56では月/季節への件数重み付き再集計、下層の時刻subset、固定代表点の風配を加える。原気象場を復元して飛行する接続ではない。人工データの気象画面・季節計画は資料を明示して別に残る。以下は現在のソースに対応する操作で、実UIの受入済みを意味しない。受入・未確認はS36に記録する（0.46の画面統合実績はS35）。

### 初回の依存と画面ビルド

Node.jsは `frontend/package.json` の下限を満たす版、Pythonは3.12を使う。専用のbackend/.venvへ固定requirementsを入れる。npm ci/pip installは依存配布先へ通信する。requirements.lockは版の固定で、wheel hash lockではない。

```powershell
python -m venv backend/.venv
& backend/.venv/Scripts/python -m pip install -r backend/requirements.lock
npm --prefix frontend ci
npm --prefix frontend run build
```

`frontend/node_modules`、`frontend/dist`、`backend/.venv` は再生成可能なruntimeで、正本ソースや唯一の結果の置場ではない。buildはReact画面に加えて、現役sourceの `frontend/scene3d` を `dist/scene3d` へ、npmで解決したCesiumを `dist/cesium` へ配置する。旧模型ZIPのvendorを別に手作業でコピーする手順ではない。出典と配布の境界は [SCREEN_PROVENANCE](../frontend/SCREEN_PROVENANCE.md) に戻る。依存不足やbuild失敗時は出力を確認し、別の既存Pythonへ無言で切り替えない。

### 起動と画面の使い分け

```powershell
& backend/.venv/Scripts/python -B -m uvicorn backend.app:create_app --factory --host 127.0.0.1 --port 8451
```

同じPCのブラウザで `http://127.0.0.1:8451/` を開く。APIが `/api/v1`、画面資産が `/assets`、独立3D画面が `/scene3d`、Cesiumが `/cesium` で配信される。起動前に `$env:BALLOON_DATA_DIR = 'C:\任意の保存先\balloon-state'` を設定すれば別の保存先を使える。省略時は `%LOCALAPPDATA%/BalloonSimulator/state`。検査用に別buildを配信する場合は `BALLOON_FRONTEND_DIST` をその絶対パスへ設定する。同じ保存先を二つのserviceから同時に開かない。上の例はloopbackへ限定したローカル起動である。

1. 「打上げ計画」の「表示するデータ」で「保存気象・実計算」を選ぶ。旧版の表示名は「固定GFS・実計算」で、0.53候補では保存JRAも同じ入口から選ぶ。北海道/和歌山のGFS例や東海のJRA例は固定された過去の入力で、最新予報ではない。資料名、解析/予報の区別、有効UTC、支持範囲を読む。この名称と保存JRAの代表操作は0.53の実画面でも確認した。
2. 必要な候補を追加し、条件棚で入力を編集する。一飛行なら「標本の作り方」の「計算方法」を「指定条件の一飛行（n=1）」にして「この条件で計算」を押す。延期系列は親の条件から時刻差を持つ草案として作る。系列の作成だけでは計算しない。親の計算操作は親と延期列を対象にする。入力編集中も、旧固定結果は別の計算時の版として保持される。
3. 候補タブ、共有地図、詳細の履歴と時刻操作で結果を読む。実n=1には50/90/95%の分布域を生成しない。着地と支持不足等による停止を区別し、停止時の最後の有効位置を着地点とみなさない。灰破線の水平境界に加え、高度/時刻の支持も確認する。保存視点がない初回は結果の読込み後に全体へ合わせる。保存した視点や、その後のパン・ズームを状態の再確認で巻き戻さない。詳細の風速・風配の軸は選択標本の本数を整数で示し、n=1を確率分布に読み替えない。
4. 表示結果の選択欄、または「保存結果を開く」で固定runを選び直す。入力を変えた草案と、表示中の計算結果が同じ条件かを確認する。図やKML等の出力は現在表示対象の保存であり、project全体の別PC移送とは区別する。
5. 「気象を分析」は「保存した実気象集計」を開く。「集計する資料」で新2024年JRA-3Q/ERA5原標本または提供済み10年DBを明示して選ぶ。接続と対応する図は下記の「実原標本で、中央値・幅・時間帯を分析する」と「提供済み10年DBを分析する」で資料別に確認する。「表示するデータ」を「画面確認用の人工データ」へ替えると、従来の四つの気象画面と地点/時期を季節計画へ渡す操作を使える。0.55の「季節計画」には下記の原日時比較があり、人工データの画面とは切り替えて使う。

背景の「未接続」という利用状態を選ぶ項目は0.47で取り除き、通常の地図または衛星・航空写真を表示する。地図表示は地理院タイルへ接続する。写真3Dは引き続き明示接続である。保存場の数値計算そのものは、地理院やGoogleへ通信しない。背景地物と計算に用いた地形の精度は同じではない。

### 保存JRAの一窓で本命と延期を比べる（0.53候補）

上の同じbuild・起動手順を使う。新しいJRA取得service、APIキー、DuckDBの起動設定は不要である。保存JRAの計算は原NetCDFや取得時の外側pathを読み直さない。これは取得済み実気象を画面で使う行程で、任意の過去日時をダウンロードするUIではない。以下は0.53候補で実行した代表手順である。別版・別環境では、秒や由来表示を含む対応を確認して使う。

1. 「共通の準備」→「気象の準備」の「保存済みの気象」を開き、「東海・保存JRA-3Q解析例（暫定地表接続）」を確認する。2024-01-01の00/06/12 UTC、100モデル面と対象範囲、モデル地形・暫定再構成の注意を読む。「配布一覧を更新」やGFS取得操作は、この保存例を使うためには押さない。
2. 「この保存例から候補を作る」でC-11の入力例を作り、機体・放球地点・幾何ASL高度・最大時間を確認する。初期日時は **2024-01-01 11:17:13 JST（02:17:13 UTC）**。既存候補に「選択候補へ適用」した場合は、入力例へ戻るのでなく、その候補の物理条件を保って気象だけが変わる。
3. 06 UTCを跨ぐ比較を調べる場合は、親の放球日時だけを **2024-01-01 13:17:13 JST（04:17:13 UTC）**へ明示変更する。13秒が残ることを確認する。これはC-11の既定日時を無変更で実行した例とは分ける。地点や機体は変えず、地上高度を別地点へ黙って流用しない。
4. 親候補の延期列の編集で **＋30分**を追加する。子は13:47:13 JST（04:47:13 UTC）で、機体・ガス質量・同じ保存場を継承する。親子それぞれの「放球＋最大飛行時間」が保存窓内かを確認する。「指定条件の一飛行（n=1）」で親の「この条件で計算」を押す。各候補は別受付なので、一方の拒否を両方完了と読まない。
5. 共有地図と延期列で固定結果を選び、軌道・着地または停止・元日時を比較する。必要なら検査用と明記したGeoJSON領域を読み、該当した同じ結果から詳細へ進む。n=1は点と軌道であり、50/90/95%の分布域や校正済みの干渉確率ではない。CLIとの数値比較では画面が受理した各固定入力と同じ場・数値環境を使い、全records・events・status/summaryを比較する。候補名・run ID・出力pathの差は分ける。
6. 地図・詳細時刻・選択対象を確認して「計画を保存」する。同じ保存先で再起動し、「保存結果を開く」→「保存した計画を読み直す」で親子、固定結果、領域・選択・時刻を確かめる。草案を編集しても、表示中の旧結果は以前の入力・気象に固定される。再読失敗は下の再読操作を使い、再計算で上書きしない。

現在場と固定結果の資料が一致しない表示、利用不能、照合情報不足は、入力差分や結果の未読とは分けて読む。現在場が無いことは保存resultの欠損を意味しない。旧票のhash不足も「別内容へ変わった」と断定しない。現在の資料名やhashで旧結果の来歴を更新せず、新しい計算が必要なら明示して固定結果を作る。場の初回読込・検査、待ち行列・計算、結果読込/描画、保存再読の費用を分け、保存場利用の通信0を新規取得の速さと呼ばない。

北海道の半月風統計からこの東海窓を選んだ実証ではない。当時未実装だった原日時の複数窓は、0.55の明示比較へ接続する。任意過去日時の新規取得UI・多年を代表する季節MCは未了である。再構成の定義とCLIの保存例は[C-11](#C-11)、由来の四状態は[実装ノート](IMPLEMENTATION_NOTES.md#IM-JRA-GUI)へ戻る。

### 実際の予報を準備する

「共通の準備」→「気象の準備」から始める。既存の保存例の場を、実際に選んだ予報へ替えるための行程である。

1. 「配布一覧を更新」を明示して配布中の初期時刻を観測し、使う初期時刻を選ぶ。固定runを調べる場合はUTC欄へ入力する。観測時刻と一部失敗の有無を読み、選択中のrunと今回観測した新しいrunを区別する。選択中のrunが新一覧から欠けても別runへ自動で替えず、「この観測で配布未確認」と示す。新しいrunを使う場合は明示して選ぶ。一覧は観測時の配布ファイル名であり、GRIBの内容を検査済みという意味ではない。
2. 対象候補を選ぶ。延期子は親と一緒に含め、秒を含む放球時刻から最大飛行時間までの必要窓を表示する。全対象の放球点を含む範囲（「範囲へ合わせる」で地点群へ拡張できる）、raw入力・作業メモリ上限を指定して「取得計画を確認」を押す。この段階では外部取得しない。
3. 「固定計画」で必要窓と取得する有効時刻、外向きに丸めた範囲、量の概算を読む。「取得範囲を地図で確認」で橙破線と候補を比較し、「取得条件へ戻る」で調整する。取得条件や延期列の必要時間窓を変えたら再計画する。配布・依存・上限不足がある計画は開始しない。
4. 「この固定計画で気象を取得」を明示する。待機/保存rawの照合・コピー/取得/復号とファイル数・新規通信/再利用bytesを確認する。同じ正規化要求・復号器の完成場は照合して再利用する。窓を延ばした場合も、登録済み完成資産に同じrun・lead・量指定・丸め後矩形・URLのrawがあり、bytes/hash等の検査を通れば独立にコピーし、不足時刻だけ取得する。コピー後は新しい全時間窓を現在の復号器で検査する。例えば6時刻から7時刻への拡張で必ず1時刻だけの通信になるとは限らず、一致する登録資産と正常なrawが必要である。取消は処理途中の安全な境界で反映されるため、取消要求と取消完了を区別する。
5. 完成後、適用先を確認し「完成した気象を選択候補へ適用」を押す。候補の物理入力を保ち、選択場だけを替える。取得完了だけでは候補や旧計算結果は変わらない。条件棚で放球地点・時刻・高度を確認し、新しい計算を実行して固定結果として比較する。

放球地点や選択気象を変えたときは、条件棚の「モデル地表を確認」で、その場のモデル地表と現在の幾何ASL高度との差を読む。必要なら地表からの余裕を指定し、「地表＋指定高さを放球高度へ反映」を押す。照会だけでは入力は変わらず、移動前の応答を別地点へ適用しない。既定の5 mは入力の提案であり、現地の必要高度を決める値ではない。計算に使うモデル地形は粗く、実DEM・建物・樹木とは異なる。この一点の地表が取得できても、全高度の気象支持や全飛行を保証しない。

時間窓は取得時と計算時の両方で検査する。取得後に延期列や最大飛行時間を延ばし`WEATHER_WINDOW_UNSUPPORTED`となった場合は、新しい必要窓で気象を準備する。単に放球時刻が入っているだけでは足りない。範囲・高度支持を飛行途中で外れる場合は停止結果として読む。完成した場の上端最小値や30 km支持は、任意の破裂条件まで全軌道を解ける保証ではない。

raw入力上限は新規通信・再利用raw・保全partialの合計に対する受付制限で、節約した通信量やgzip容量を示す値ではない。一致候補に破損や同URLで異なる内容があれば停止するため、再利用失敗を黙ってダウンロードへ置き換えない。

取得失敗/取消/中断は原rawと失敗理由を残す。「同じ計画を再試行」は照合後に再開し、自動で別runへ替えない。`SOURCE_CHANGED`ではコードと起動状態が違うためserviceを再起動する。復号器も変わり`DECODER_CHANGED`となる場合は新しい計画が必要で、同じ仕事を無条件に再開しない。保存閲覧と取消は引き続き可能。依存不足は同じbackend環境へlockを導入して再起動し、別Pythonの成功を流用しない。

「状況を取得できない」は、取得処理が失敗したと確定した意味ではない。画面は最後に確認した状態と時刻を残し、実行中の仕事を間隔を延ばして再確認する。「状況を確認」は保存された仕事のGETであり、「同じ計画を再試行」と異なり取得処理を再送しない。初期の資料一覧・依存情報・取得履歴の読取り失敗も、表示された再確認から読み直す。現在の入力・選択run・固定計画は保持する。

### 仮幅を固定し、対応する集合を比較する

親候補の「条件を編集」→「標本の作り方」で、「計算方法」を「一変量の仮幅を共通標本で調べる」にする。今回の選択は次の三つで、比較に含める全候補がその量を使う必要がある。

| 「変える元量」 | 単位 | 使える方式 |
|---|---|---|
| ガス質量 | kg | 等温浮力上昇。破裂後の下降質量を同時に変える入力ではない |
| 破裂高度 | m | 高度による破裂。海面基準で、径破裂には適用しない |
| 基準下降速度 | m/s | 定格速度による下降 |

1. 「下端」「上端」「標本数 N」「seed」と「一様分布の仮幅を置く理由」を入力する。下端 < 上端にする。初めに表示される同じ値の上下端は、採用済みの幅ではない。気象誤差・製品の校正済み分布・事故確率の入力とは区別する。
2. 親の延期列は一緒に含まれる。モデル等の違いも比較するなら「同じ実現値で比較する独立候補を追加」で選ぶ。全候補に同じ固定気象と同じ元実現値を使う。延期子では時刻だけが変わり、モデルを変えたい場合は独立候補にする。候補ごとの結果を一つの分布へ混ぜない。
3. 「標本と計算入力を固定して確認」を押す。予定試行数、入力不成立数、元実現値、必要な時間窓と固定気象の有効範囲を読む。この操作だけでは飛行しない。候補数 × Nは256以下、同時進行集合は4以下という初期の運用制限がある。適切な標本数を保証する値ではない。
4. 固定内容を確認して「この固定計画で実行」を押す。入力や比較候補を変えたら、古い計画を使わず固定し直す。時間窓が不足する候補名と終了時刻が出た場合は「気象の準備」でその窓を含む場を取得・適用するか、放球時刻/最大飛行時間の意味を見直してから再計画する。実行可能にするためだけに飛行時間を切り詰めない。
5. 状態別の数を確認し、固定結果ができたら「この集合の候補を表示」を押す。計算や再開の完了だけでは地図の旧結果を置き換えない。着地L/予定Nを読み、50/90/95%は得られた着地点の経験的な包含域として見る。停止・未実行・失敗を非干渉着地へ含めない。点や線に退化した結果にも、人工的な幅を足さない。
6. 「共通の準備」→「落下を避ける領域」からGeoJSON/KMLを追加する。「この候補を詳しく →」の「干渉」で該当した着地群を選び、元量の分布・「全予定試行の入力・終了理由」・相別履歴を読む。「全記録」で予定Nへ戻り、地図上の囲みや一点選択でも掘り下げられる。干渉H/着地Lの割合を、全予定の安全確率とは扱わない。領域や標本の選択を変える操作は集計だけで、飛行を再計算しない。
7. 見たい固定結果と群を選び、分析の読込み完了を確認して「計画を保存」へ進む。図を渡す場合は詳細の「PNG保存」「SVG保存」を使う。群は固定結果と領域に対応して保存され、再読時に一致しなければ全予定試行へ戻った案内を読む。古い群を新しい結果へ無言で適用しない。

「残る試行を取り消す」は実行中の一飛行を強制終了せず、未開始分を止める。「未完了の試行を再開」は未投入・取消・中断・実行失敗の行だけを同じ実現値で再投入する。着地・物理停止・入力不成立を成功するまで引き直す操作ではない。仮幅や物理条件を直す場合は新しい固定計画を作る。再開前のsnapshotも残り、保存結果一覧で以前の計算回を選べる。

履歴集計の対象 `result.json` 合計が64 MiBを超えると、履歴の未生成理由と省略数を返す。着地点・経験域・予定数・原履歴は保持するので、地図で対象を絞って再分析する。空の履歴図を「飛行しなかった」と解釈しない。これはサーバ側の履歴集計を受け付けるための制限で、ブラウザ通信量やプロセスの実メモリ上限保証ではない。詳細の原履歴は、固定snapshot/caseの現在選択IDのうち結果が利用可能な記録を、集計の完了・64 MiB制限・送信権から独立して画面内で最大4件ずつ読む。集計上限を超えた選択群でも原履歴を読めるが、履歴cacheや総通信量の上限を保証するものではない。表示読込みだけが失敗した場合は「表示データの読込を再試行」を使い、物理試行の再開と区別する。

集合の状態を取得できない場合、画面は「現在の状態を確認できません」と最終確認時刻を示す。表示件数は最後に読めた値であり、計算の失敗・停止の確定ではない。集合関連のGETは応答本文を含め30秒で読取りを打ち切る。進行中集合の状態確認は読取り完了/失敗後に通常0.9秒待機し、失敗が続くと次の確認までの待機を最大15秒まで延ばす。応答を待つ時間は別に掛かる。「状況を確認」はGETだけを行い、計算・取消・再開のPOSTを再送しない。別の送信エラーは状態GETの回復で消さない。画面の保存再読/終了では旧監視を解放し、表示中の固定結果を保つ。

### 実原標本で、中央値・幅・時間帯を分析する


JRAは同じ出力先を指定すると成功応答をURL/bytes/SHAで再検証して再利用する。ERAの既定transportは`dods`で、NCSSへは`--transport ncss`で明示切替する。NCSS復号には既存環境のSciPyが必要で、未導入なら通信前に停止する。既存出力への再開は上のERA引数へ`--resume`を追加し、`--months`には既に公開した月を先頭から含める。例えば1–3月完成の束を全年へ進める場合も、上の1–12月の全列を指定し、既存月を省かない。検証済みDODS応答と完成月checkpointを再利用し、不足標本だけをNCSSへ要求する。両応答が存在するときは復号値・UTCの一致も検査する。新規のNCSS原NetCDF bytesと票は別に残し、旧DODSの失敗や原bytesを上書きしない。

ERAの`--attempts 2`は各NCSS要求に記録する累積試行枠で、再実行ごとに2回を追加する意味ではない。旧DODSの試行履歴・最大3枠も保持し、自動でサービスを変更しない。転送中断等への再試行は指定回数までで、HTTPエラーや内容検証の失敗は停止して理由を読む。NCSS応答は1要求5 MiB上限で検査する。通信時間の設定はOS/サーバ処理も含めた実経過の厳密な上限保証ではない。推奨例は1 workerである。今回の取得では一時的に合計2要求の並行を試した後、部分受信の失敗を受け主系列1本へ戻した。workerを増やすことや枯渇した要求に追加枠を与えることは、既存の失敗票・配布元負荷・回復状況を読んだ別判断にする。実際の停止・有限probe・再開状況は[S36](../BOOTSTRAP_RUNBOOK.html#s36-era-ncss-plan570)へ戻る。

最終`manifest.json`のmonthsが1–12の全てを含み、u/v原配列の検査が通ってから年間sourceとして登録する。途中月を補間して埋めず、部分取得のmanifestを年間完了と呼ばない。原応答/取得票/旧manifestも保管する。取得器の再現範囲と配布元条件はWEATHER、帰属と固定デモは`references/climate_demo_057/README.md`へ戻る。

### 計画を保存して再開する

「計画を保存」は草案・候補の親子関係・元量の仮幅/理由と、表示する固定runまたは集合snapshot/case参照に加えて、用途別の `ui_state` を保存する。予報では候補/群の選択、表示・色、禁止領域、詳細指標・時刻、地図/衛星の背景種類・位置/高さ、3Dの軌道とカーテンの表示状態等、気象では分析条件等が保存対象である。保存された内容の詳細は [IMPLEMENTATION_NOTES](IMPLEMENTATION_NOTES.md) に戻る。Googleのキー・接続、ブラウザの一時対話は保存対象に含めない。

人工候補だけの書出しは候補メニューのJSON保存を使い、読込みは「すべての候補 · ＋」内の「人工候補JSONを開く」から行う。これは上記APIの計画保存・固定run読込みとは別の形式で、実計算表示では入口を出さない。実候補を削除しても固定runは残るが、草案の即時取消は未接続である。人工候補の削除直後の取消とは区別する。

未保存の表示を確認してから保存し、ブラウザやserviceを閉じる。同じ保存先で起動後、「保存結果を開く」から「保存した計画を読み直す」を使って草案・固定結果・画面状態を確かめる。別の集合結果を見る場合は同じ一覧の「固定集合を表示」で計算回と候補を選ぶ。保存内容の再読は今の未保存編集を置き換えるので、仕事の状態だけを確認したいときは下記の再確認を使う。保存や再読だけで新しい計算は送信されない。科学結果は不変のrun/snapshot参照として読み、再試行の最新結果や画面状態で書き換えない。

単便の状況は画面上部で確認できる。通信失敗時は最後の確定状態・確定時刻を保ち、実行中の仕事は自動再確認する。「状態と結果を再確認（再計算なし）」はGETだけを行い、新しい計算を送信しない。計算終了と結果の読取り成功は別なので、結果の読取り中断も計算失敗へ変えない。単便/気象準備の各GETは応答本文を含め20秒で待機を打ち切り、正常な観測の後は約0.9秒、失敗後は約1.8秒から最大15秒の間隔で次を確認する。これは1 GETの期限で、複数のGETを使う観測全体の所要時間ではない。集合の30秒期限は前節のままである。入力編集中や別の固定結果を選んだ後に旧応答が届いても、草案やその表示選択を取り消さない。

保存結果の復元中は「保存結果を読込中」とし、未計算・0標本とは区別する。読取り失敗や保存先の404はそのまま表示する。「保存結果を再読込」は保存済みrun/caseのGETを再試行し、新しい軌道計算や気象取得を開始しない。表示する選択群・干渉群に保存済み集計がない場合は、表示側が別途その集計を作成することがある。保存分析への参照が一致すれば分析もGETで復元する。概要・3D・KMLは干渉した個別着地点を示し、外周だけのための集計は要求しない。干渉群全体を調べるときは件数または詳細の「干渉」から進む。風統計の「保存した図を再読込（再集計なし）」は固定した図のGETであり、元DBを再集計しない。詳細の選択群と時刻、比較参照、未適用の草案は復元を待つ間も保持する。時間範囲が未読の間は保存時刻を表示し、時刻バーは結果の読込後に表示する。保存先の404は再読ボタンで結果を再生成するものではない。

0.55の詳細修復では、全標本を選んだ場合は固定caseにある全体分析を再利用し、原履歴のGETは追加集計の受付から独立して進める。部分群を全体分析で代用しない。読込中・失敗・送信権待ちを画面に残し、明示した再試行で同じ対象を読み直す。送信担当になった際に再開できるのは、権利不足でまだ一度も送っていない派生分析だけである。受付が不明な送信を自動再送せず、詳細を見るための飛行再計算や保存草案の再送も行わない。

serviceは同時1飛行・最大4待機で、集合も同じworkerへ順に投入する。直接n=1の取消は待機中だけ。集合の「残る試行を取り消す」は未開始分を止め、実行中の一飛行の結果を残してから取消を終える。端末のCtrl+Cによる正常終了も実行中仕事を待つ。再起動時は完成物の照合・回復を先に行い、なお未完の集合と投入済の仕事をinterruptedへ移し、未投入行は未投入のまま残す。自動再送しない。ブラウザ再読は既存仕事を観察し、後着結果で保存済みの比較選択を置き換えない。 ただし受付不明の固定要求を明示照合して回復した単便は、その候補の表示選択が空で、草案が送信時点と一致し、選択世代も変わっていなければ初期表示へ入る。編集後の草案や既存の比較選択を回復結果へ置き換えない。応答不明の単便・集合要求は、ブラウザ再読後も固定本文と同じ要求IDを保持する。下記の受付回復節に従って確認・明示再送し、編集した別入力へ置換しない。受付後の新しい「計算」操作は新runになる。原場が後で不足しても固定結果は読めるが、再計算可能とは限らない。

### 原日時の複数窓を、共通機体で比較する（0.55）

「季節計画」→「保存気象・実計算」が入口になる。「気象を分析」の固定集計から「打上げへの影響」へ進むと、関心の半月/月/季節・元半月ID・気象有効時刻subset・領域・集計出典を渡せる。期間はUTC暦のまま、気象有効時刻を放球時刻へ自動置換せず、次画面で原年と原放球日時を別に選ぶ。半月平均から瞬時場を生成する操作ではない。人工データは切替で残る。

1. 「原日時の比較候補を追加」で保存場の診断用入力から候補を作り、「条件を編集」で地点・ASL・機体・最大飛行時間を確認する。各原日時へ共通適用する条件である。診断例のASLを別地点へ無条件に流用しない。
2. 「原日時を追加」で、実際の放球日時（JST、秒付き）・その日の登録場・選んだ理由を入力する。季節分析から渡された関心条件と、取得済みの日時が一致するかを利用者が判断する。未取得日は場を「未取得・未登録」のまま残せる。
3. 「原日時と計算入力を固定して確認」で、予定数と実行可能数、各日時の時刻/放球点の支持を読む。未取得・最大時間不足・領域外の行を予定から自動で除かない。この事前確認は全軌道の支持保証ではない。
4. 「この原日時集合で実計算」で同じ飛行核へ渡す。完成後「この原日時集合を地図へ表示」から、従来の地図・禁止域群・履歴・図保存へ進む。全予定数、着地数、停止/不成立を分ける。少数日時の経験域は将来の落下確率ではない。
5. 原日時・理由・共通機体を変えたとき、表示中の固定結果は以前の計算に残る。新計画を確認して実行するまでは変更前の結果として読む。「計画を保存」で草案の日時一覧、固定計画/結果への参照と画面を保持する。

登録済みのJRA例以外は、起動前の `BALLOON_HISTORICAL_CATALOG` にローカルJSONの絶対pathを指定する。schemaは `balloon.historical-catalog/1`、`sources` の各要素に `id`（historical-で始まる一意名）、`label`、`path`（catalog基準の相対pathも可）、保存bundleの `sha256`、任意の `default_config` を置く。原UTCのJRA modelまたは明示B schemaだけを受け付ける。C-10は旧小領域原本からstrict場への固定変換、C-11は既成B場の飛行例であり、任意NCSS応答の汎用変換器ではない。今回の北海道2窓はS36の固定原応答と外側normalizerへ戻る。Webから任意pathを開かせるAPIではなく、任意年月の自動取得UIもまだない。catalog一件が壊れても旧固定結果の閲覧は独立している。

### 受付が分からなくなった場合と、保存先の同一性（0.55）

送信前の完全な入力・要求IDはブラウザのlocalStorageへ保存し、送信の待機は60秒で打ち切る。時間切れは未受付の証明ではない。単便と延期列は一件ずつ投入し、再読込み後は勝手に続きを送らない。「受付を確認（読取りのみ）」で同じ要求IDを調べ、未送信分の続行は明示する。集合も保存した同一ID・本文で確認/再送し、現在の編集中入力を混ぜない。

ブラウザの未確定要求は保存先の不透明なinstance IDへ結び付く。同じURLでもinstance IDが異なる台帳には、旧要求を自動移植しない。独立に初期化した保存先には別IDが付き、同じ台帳のバックアップ・複製は同IDを保つため、複製や巻戻しを検出する機能ではない。旧未束縛要求や形式不正の記録も削除せず保留する。ブラウザの保存消去や別PCへの自動引継ぎを保証する仕組みではない。

計画保存の応答が不明なら「保存先と照合」で送信時点の草案・revisionを確認する。送信後の編集も保持される。異なる保存版が見つかった場合は相違を読み、どちらを基準にするかを選ぶ。通信回復だけで現在の草案を上書きしない。計算器停止の表示が出た場合は保存結果を読みながらserviceを再起動し、未完了分を明示再開する。完成ファイルが揃った実行は固定specと全出力hashを照合して回復し、不完全な仕事を完了へ変えない。

同じブラウザの同じorigin（scheme・host・port）では、送信担当を一つのタブに限る。他のタブでも保存結果・地図・接続済み3Dは閲覧できる。0.55修復では、起動時は空いている権利だけを取得し、別タブの担当を自動で移さない。「このタブで送信権を取得」を明示クリックした時だけ、既存担当へ協調引継ぎを求める。別タブを探して閉じることを通常手順の前提にしない。実際のWeb Lockを取得するまでは閲覧用のままである。既存担当が受付/台帳更新の一連の処理中なら途中で奪わず、処理中の理由を返して今回の取得を終了する。処理完了後にもう一度取得をクリックする。8秒応答がない旧版/休止タブ等は理由を表示し、強制取得や再送で解消しない。切替えは草案・表示・キー/接続を保持し、残った固定要求の再開は受付確認後に明示する。Web Locks未対応時は送信を止め、別origin・別ブラウザ・CLIまでの排他制御は主張しない。新14で確認した詳細閲覧と同版タブ間の引継ぎ、旧版タブの8秒無応答、未確認範囲は[S36](../BOOTSTRAP_RUNBOOK.html#s36-detail-lease-repair550)へ戻る。

### 同じ表示対象を3Dで確認する

地図の「3Dで周辺を確認」で、現在の対象を独立rendererへ渡す。Google写真3Dを使うときだけ、その画面の入力欄へMap Tiles APIキーを入れ「Google写真3Dへ接続」を押す。キーは保存計画・出力やURLへ書かない。接続には外部要求と利用枠の消費がある。同じ打上げ計画画面内での2D/3D往復は同じ接続を保持する。実計算/人工データの切替、気象/季節への用途移動、保存計画の再読込みでは画面が破棄され、3D接続も終了する。自動再接続はしない。これらの切替後や解除後に写真3Dを使う場合は、改めて明示接続する。

概要では表示中の注目候補、詳細では現在の選択群の同じ経路を、地表投影線と空中線で読む。「軌道＋地表線」は二本を一組で切り替え、「カーテン」はその間の薄い幕だけをOFFにできる。どちらも既定はONで、軌道をOFFにすると幕も隠れ、幕の選択値は保持される。この二つの表示設定は「計画を保存」の `ui_state` とKMLの初期表示に共通して使う。候補や表示設定の通常更新では視点を保持し、「軌道全体を見る」を押したときに経路全体を見渡す位置へ移る。これらは固定した飛行結果を再計算する操作ではない。

実結果の空中線は保存ASL高度を使い、3D表示だけで同梱EGM96を加えて楕円体高へ換算する。科学計算とKMLの元高度は変えない。人工結果の高さは地物からの高さと見立てた模式AGLで、実飛行高度ではない。地表投影や幕は地物との接触・衝突判定を表さない。高度基準の詳細と限界は [実装ノート](IMPLEMENTATION_NOTES.md) の「3Dの地表投影と空中経路」へ戻る。

実ASLのカーテンは、全経路の空中線と地表投影線の上下関係を読むための連続した幕である。幕を表示用の地下下端まで延ばし、不透明な地物メッシュに隠れる部分を深度描画で遮る。下端は地形の推定値ではなく、下端の線も描かない。写真メッシュに穴がある、またはまだ読めていない場所では地下へ延ばした余長が見える場合がある。「軌道全体を見る」の範囲にはこの地下下端を含めない。実経路の空中線・幕はGPUで地物高を取得せずに描くため、旧「地物への接続」の待機や更新操作は実結果には表示しない。

人工AGLだけは空中線の上端を決めるために地物高を必要とし、全節点が揃うまで全相の空中線と幕を一括で保留する。地表投影線は残る。必要な場所へ近づいて表示の静止を待ち、必要なら「人工AGLの高さを再確認」を使う。一回の照会と経路の分割数には上限があり、長い経路や読込みの届かない場所では全点が揃わず保留が続く。この制限を、地物高の取得を必要としない実ASLへ広げない。経路表示や人工AGLの再確認のためにGoogleのroot接続を作り直すことはなく、同じ接続中のタイル読込みとは区別する。

以上は0.55の連続幕への変更を含む操作説明である。新版の実写真上での全経路表示・切替・2D復帰・候補更新と最終試験の実施範囲、残る制約は[S36の実装結果](../BOOTSTRAP_RUNBOOK.html#s36-route3d-results550)へ戻る。地物高を取得した区間だけ幕を出した旧方式の実写真観察を、新方式の成功へ読み替えない。

外部写真へ接続しない人工地表の確認入口は `http://127.0.0.1:8451/scene3d/index.html?probe=synthetic`。これは投影・名称・描画処理用の人工fixtureで、実地物の確認ではない。写真上の輪郭・禁止領域・軌道の関係と、2Dへ戻った後の継続操作は、実接続の観察記録と分けて確認する。0.40.1での観察を、そのまま0.46の受入結果へ転記しない。

## C-10：固定JRA-3Q原本から飛行を計算し、支持不足を読む

この経路は、repoに保持した`references/jra3q_model_fixture/source_bundle.json`の2024-01-01 00/06 UTC・100モデル層・2×2格子を、飛行CLIが読める保存場へ変換する。原本のダウンロードや別時刻の取得は行わない。北海道の半月統計DBとは別の資料である。この旧strict例は支持停止を読む対照として保持する。0.52の地上全飛行は別入力の[C-11](#C-11)へ進み、任意過去窓の取得画面と代表性を定めた多年の季節MCは未実装である。登録済み原日時の有限比較はC-09の「原日時の複数窓」へ進む。
