# 1. 推奨する基本構成

## 1.1 GitHubを現在状態の一組として扱う

採用ブランチmainの現行ファイル群を、その時点から次の開発を決められる状態にする。ソースコードだけでなく、現在の目標・仮定・理由・重点・未解決条件・必要な教訓を含む。過去に何をしたかを全件読み直さなければ意味が分からない配置にしない。

| 保存先 | 現在の責務 |
|:--|:--|
| 非公開GitHub `GENIANY/space-balloon-simulator-jp` / main | 承認された現在の一組。安定パスにコード、編集元、現行文書、台帳、必要な参照資料を置く |
| 作業ブランチ | 基準SHAからの変更候補。中途半端な移行をmainの現行状態にしない |
| ローカルPC | 固定したmainからの変更候補を作成・検査する。旧ZIP・過去版・復旧スナップショットは候補と分けて保持し、未統合の候補を承認済みmainと混同しない |
| ChatGPT Project | 利用する場合の正本への短い入口。一時的なAI探索資料等を置けるが、正式仕様の二重編集元にしない |

Projectは正本への短い入口であり、頻繁に変わる仕様の二重編集元にしない。未採用のAI調査資料は探索用に扱う。提供原本Excel3冊はPR #13でmainへ統合され、M101の固定取得とSOURCESのハッシュ照合まで確認された。Project側の原本削除や、原本の科学的妥当性・公開許諾の確認まで済んだという意味ではない。正式に採用する主張・制約・比較条件は、一次資料等の根拠とともにGitの担当文書へ受け入れる。元資料がProjectにあることと、採用状態がProject側で決まることを分ける。

版を進めるたびに新しいディレクトリを作らない。ファイル追加・配置変更は役割が増える、分割が必要になる等の理由があるときだけ行う。0.3でのlegacy解消は旧配置の一度限りの是正であり、毎回の改訂パターンではない。

Gitのコミット履歴を消す、リポジトリを作り直すという運用は行わない。組込み履歴は変更管理の手段であって、最新の意味を過去へ探しに行く前提にはしない。次に効く理由は現在のDECISIONS/LESSONSへ受け入れる。

## 1.2 「完全性」の範囲を定義する

完全性は「過去の全発言を保存すること」ではない。最新仕様、理由、制約、却下した選択肢、未知の点、未完作業、再開方法、検証証拠が、会話なしで復元できることを意味する。採用しなかった案でも、再提案の誤りを防ぐ理由や再検討条件があるものは残す。

二つの復元水準を分ける。第一は**開発継続の復元**で、現在のコード・文書・小さな固定入力・テストが必要である。第二は**特定の過去計算の完全再実行**で、その計算が使用した入力データの実体まで必要になる。URLとハッシュだけでは、削除された外部データを復元できない。大容量の気象データについて、保存対象・保存期間・保存場所・再取得不能時の扱いを決め、完全再実行できない計算をできるものとして表示しない。

## 1.3 情報には所有者と性質を付ける

同じ値を複数の編集元に重複させない。ただし、人間向けPDFや一覧表に同じ値を表示することはよい。その場合は正本から生成する。コードは実際の挙動、要求は期待される挙動、テスト結果は特定条件の証拠である。三者が食い違った際に、単に新しい方を正解として処理してはならない。不整合として登録し、判断して修正する。

承認、実装、検証、公開は別状態とする。「実装した」と「試験に通った」と「mainへ統合された」を一つの done にまとめない。外部Projectを利用する場合も、そちらの反映は別の観測として扱う。

現行の責務は、要求・重点をPROJECT_CONTEXT、採否と判断理由をDECISIONS、手順・実施状態をBOOTSTRAP_RUNBOOK、課題・未確認をBACKLOG/UNCERTAINTIES、確認範囲と証拠をCONTENT_HEALTH、版とGit遷移をVERSION_HISTORYが持つ。Codex専用の別の進捗台帳を増やさず、担当者が変わっても同じ記録から判断を続ける。

# 2. 三つの開発目標を検証できる要求に変える

## 2.1 日本周辺への最適化

主な方向は、事前指定した領域の入力で処理量を抑え、将来的に日本語GUIを備えることである。領域は日本に固定しない。地図の初期表示だけを変えることでも、全球の情報を必ずすべて常駐させることでもない。必要な飛行範囲を覆うデータと、境界に近づいたことを把握できる仕組みを組にする。

地域・高度・時間・季節を最初のケースに対して具体化し、必要な支持点・欠測・範囲外を明示する。約30 kmという規模は取得高度の上限そのものではない。必要な層・変数・期間を実ファイルで照合する。領域切出しによる性能改善と、予測精度が改善したとの主張は別に評価する。

着地・着水には地形、必要に応じて陸海の分類を使う。放球位置は緯度・経度とその位置の標高＋地面からの相対高度で指定できる経路を検討し、絶対高度指定も残す。高さの基準と入力の意味を表示する。地形製品、座標・標高基準、海・湖・陸、欠測、領域外での挙動は、実装前の判断項目とする。

## 2.3 Tawhiriより高度なモデル

以下の既存実装・ライセンスに関する説明は2026-09-16の調査記録である。現在の配備や利用条件の再確認ではない。

Tawhiriの公式API文書の標準プロファイルは、一定上昇率、指定高度での破裂、海面基準降下率に基づくパラシュート終端速度降下を説明している。float_profile も記載されている [S01]。一方、設計文書自体は、モデルの合成や飛行段階の連結を考慮している [S02]。したがって「Tawhiriは拡張できない」という前提には立たない。

今回確認した原リポジトリの基準候補は `cuspaceflight/tawhiri` であり、コミットは次のIDである [S03]。

```text
668b44e5b88a66e0d885a9f9b16ff507d856bbbd
```

これは公開サービスや派生版の運用コードと同一であることを意味しない。比較対象を決める際は、原版、派生版、公開APIを区別する。READMEのライセンス表記はGNU GPL 3である [S04]。コード流用方針と依存物の扱いは実装開始前に決定し、式や設計を参考にすることとコードをコピーすることを区別する。

高度化は、例えば気体・膜の温度、膨張、浮力・抗力、相対速度、ガス損失、破裂条件、パラシュート展開、ばらつきを追加することで定義できる。RPT-027/D-139で定めた初期等温の浮力・抗力・理想気体モデルと拡張条件は第10.4節に示す。それ以外の高度化は追加候補であり、採用・妥当性確認を意味しない。**複雑なモデルを実装できることと、予測精度が改善することは別の受入条件**にする。

原版、派生版、公開APIは区別し、比較対象のコミット・条件をT-004で固定する。旧調査で記録されたSHAは、今回の基準採用を自動的に決定するものではない。式や考え方の参考とコードの流用、運用サービスとの一致も分ける。

追加実験で特定機体のパラメーターを精密に決める計画は採らない。必要入力が入手でき、物理的意味と適用条件を説明できる有望な候補を、特に上昇・破裂・下降で絞る。どれが最適かを確定できない場合も、比較の目的と限界が明確なら現役の比較機能として扱う案がある。すべての候補を無期限に残すことは要求しない。

# 3. 恒久的なファイル体系の案

コードと文書は同じ変更単位でレビューする。将来のGitHub Issues等を使う場合も、タスクの正本をCSVと二重管理しない。初期はリポジトリ内CSVを正本とする案を推奨する。外部課題管理を正本に移行するなら、理由を記録し、復旧用に必要な状態・コメント・添付証拠をエクスポートする。

## 3.1 ファイル契約

各論理ファイルには、最低限、論理ID、パス、目的、読者、権威区分、編集元、依存先、内容仕様、更新契機、担当役割、検証方法、保持方針、Projectへの掲載方法を定義する。レジストリは「目的と管理方法」、マニフェストは「その版に入る実ファイルのサイズとハッシュ」を担当する。

例えばPROGRAM_GUIDEは、目的を「現在の実装で変更対象を探す地図」、非目的を「理論導出や過去版比較」と定める。編集元はTeXの説明とコードからの自動抽出データ、生成物はPDFと検索用テキスト、更新契機は構造・API・責務の変化、検査は実在パス・公開シンボル照合とPDF目視とする。

## 3.2 形式を選ぶ規則

議論・方針・短い運用文はMD、型や参照を機械検査する状態はJSON、行として比較・抽出したい台帳はCSV、複雑な式と見取り図を人が読む文書はPDFとTeXを基本とする。XLSXは複数シートや入力支援が本当に役立つ場合に使用する。CSVとXLSXを両方置く場合はどちらか一方を編集元とし、もう一方は生成する。色だけに状態の意味を持たせない。

CSVはUTF-8、固定ヘッダー、ID列、日時・空欄・列型の規則を定める。本体のCSVはUTF-8で管理し、ヘッダーと空欄の意味を固定する。長文の導出や意思決定を一つの巨大セルに入れない。JSONはschema_versionと明示的なnullの意味を持ち、暗黙の単位やタイムゾーンを避ける。

本検討書は更新頻度と対話中の検索性を優先し、**MDを唯一の編集元としてTeXとPDFを生成**する。生成TeXも必ず同梱する。将来の数式主体の理論書・構造ガイドではTeXを編集元にする。どちらも、PDFを修正して編集元に戻す運用はしない。

# 4. 状態、判断、未知の情報を混ぜない

## 4.1 各台帳の境界

現在位置と次の操作はHTMLが担当し、別のSTATEへ手で複製しない。将来JSON等へ移す場合は編集元の移管を明示する。工程は本書第10章、課題はBACKLOG、版とGit遷移はVERSION_HISTORY、判断理由はDECISIONS、失敗から得た制約はLESSONSが持つ。現在仕様の説明に過去の修正文章を積み重ねない。

未知の項目には、仮定、未確認事実、未決定事項、リスク、既知不具合という分類を付ける。「未確認」と「確認して不適合だった」を同じ値にしない。検証期限を日付で決められない場合は、「データ源を採用する前」「熱モデルを実装する前」のような判断ゲートを設定する。

## 4.2 タスクの完了条件

BACKLOGは現在の受入と残件を表し、HTMLは具体的な手順の実績を持つ。完了には成果物、条件に対応する実測・試験、実物の用途適合の評価、関連資料の更新が必要である。Codexの実施完了、人間の採用、mainへの統合を別に記録する。未実行を成功にせず、提出したことだけで受入済みとしない。過去手順に残った未解決要求は現在の課題へ引き継ぎ、全てを現在の作業待ちとして並べない。

要求・理論・実装・試験は次の関係で結ぶ。

`REQ → ADR / MODEL → module・symbol → TEST → RUN / DATA`

例として、地形への接地を要求するREQに対し、高さ基準のADR、接地イベントの理論節、イベント処理の実装、合成地形を用いた試験、固定入力と結果を関連付ける。これにより、実装を変更したときに再確認すべき文書と試験が分かる。

## 4.3 判断記録の寿命

ADRは proposed、accepted、rejected、superseded を区別する。acceptedの判断を覆す際は、今後も効く旧理由と後継判断を記録する。全版の原文保存を現在資料の条件にはしない。現行文書の古い記述は置き換える一方で、歴史的な判断は復元できるようにする。新たなユーザー指示が以前の方針を変える場合は、その変更を記録して更新する。過去のファイルを理由に最新の指示を無視しない。

# 5. 構造ガイドと理論ガイドの作り方

## 5.1 添付例から継承するもの

添付のハイブリッドロケット燃焼シミュレータのガイドは、理論書ではなく実装の地図と明記されている。物理ページ2では、責務、読むもの／渡すもの、連携先、内部木構造、ファイル責務を階層ごとに繰り返す。物理ページ4はその枝ページの実例、ページ103は変更したい事項から読む枝を選ぶ逆引きである [U01]。

継承するのはこの説明の型であり、燃焼器のモジュール構成や物理式を気球へ移植することではない。添付された実装コード一式はないため、ガイドが実際のコードと一致しているかの監査は今回の範囲外である。

## 5.2 PROGRAM_GUIDEのページ仕様

最初に全体の処理の流れと依存方向を示し、次に枝の責務、入出力、公開API、内部構造へ降りる。枝には「してはいけないこと」も書く。例えば気象取得層は単位や時刻を正規化するが、気球の浮力式を持たない。数値積分の右辺評価中にネットワーク取得を開始しない。

自動化するのは、ファイル存在、API署名、設定項目、依存参照、索引などコードから確定できる部分である。設計意図や責務の妥当性はレビュー対象として残す。全関数を巨大な表に展開するのではなく、公開境界を本文に、細部を索引や下位説明に置く。

PDFには目次、しおり、内部リンク、章・節の安定ID、対象コードリビジョンと文書ビルドIDを付ける。横長の枝ページと縦長の説明ページを内容に合わせて使い、文字を縮めて一枚へ押し込まない。改版履歴はCHANGELOG/ADRへ分離する。

規模が増したときも、全体→枝→内部で「親の目的、この枝の責務、読むもの/渡すもの、一段下の構成、外部との関係」を繰り返す。全体図には枝間の主要契約、下位図にはその枝を理解する関係を置き、全ファイルの矢印を一枚へ集めない。目次・しおり・親へ戻るリンクも同じ階層にする。ページを増やすだけで理解を要求する関係数が増える場合は、図とコード双方の責務を問い直す。薄い再exportに一頁を割り当てるなど、ファイル数と頁数を機械的に対応させない。

ガイドは実在する構造を忠実に示す。将来の用途から必要になる責務と移行の仮説は本書第10.5節で説明し、ガイドから対応する現在の境界へつなぐ。未実装の分析やadapterを実装済みの箱に混ぜない。逆引きも「どのファイルがあるか」だけでなく「比較の標本を変える、新しい気象製品を使う、診断図を加えるときに、どの枝と横の契約を見るか」を入口とし、未実装のものは構想側へ案内する。

## 5.3 THEORY_GUIDEの節仕様

各モデルに、目的、モデルID、変数と単位、座標・高さ・時間の定義、支配式、導出、閉じるための関係式、仮定、無視する効果、パラメータの出典、適用範囲、極限での期待挙動、必要入力、数値解法上の注意、対応する実装・試験を記載する。

例えば気体温度と膜温度を別状態とする案では、式だけでなく、その自由度を増やす理由、熱収支に必要なデータ、推定する係数、観測で検証できる量、単純モデルに戻る条件を示す。入力が不十分な高度化を無条件に高精度と呼ばない。

## 5.4 再編集可能性を確保する

TeXのほかに、図の編集元、生成スクリプト、参考文献、使用パッケージ、フォント名と入手方法、ビルドコマンドを保存する。フォントファイルそのものは配布物に含めない。必要な入力が更新されたらPDFを再生成し、図・数式・表・改ページを目視確認する。TeXが存在するだけでは、そのPDFが最新版のTeXから生成された証明にはならない。

検索用のテキストは編集元またはPDFから生成し、主従関係を明示する。図の意味、数式番号、主要な表の意味はテキストでも参照できるようにする。ただしテキスト抽出で図表の妥当性確認を代替しない。

# 6. 毎ターンの読み込みと状態への戻し方

## 6.1 開始時

mainの現在コミットを取得して固定し、同じ版のREADME R0〜R5に従う。PROJECT_CONTEXTとVERSION_HISTORYで現在方針・時系列、CONTENT_MAPとCONTENT_HEALTHで内容・焦点・点検範囲を確認し、REFERENCE_LOGの現行欄とHTMLの該当手順から本文へ進む。依存関係に応じてBACKLOG、UNCERTAINTIES、DECISIONS、CONTINUITY_CONTRACT、設計・理論・実装を追加する。本書の第9/10章と課題依存も復旧時に読み、現在焦点だけへ目的を縮めない。

前回読んだファイルと理由は探索の手掛かりであり、現在の取得結果を代替しない。同じSHAの内容が実際に文脈へ残っている場合だけ再利用する。長い文書を途中で打ち切った場合は残りを取得し、未読範囲を明示する。読んだ情報はDC-JUDGMENTに従って結び付け、今回の暗黙の必要を推測し、その解釈を利用者の状況に照らして問い直してから設計する。

WORK_ORDER_TEMPLATEに基準SHA・目的・編集範囲・禁止事項・必要入力・受入条件・停止条件・返却物を定める。Codexが主担当として、必要に応じて限定した並列作業の差分を統合する。新しい判断や仮定を置いたら、採った案・採らなかった案・根拠・代償・再検討条件とともに担当する現在文書へ変更候補として戻す。コードの挙動を想像して理論書へ書かず、物理の意味を実装者が独断で変えない。

## 6.3 終了時

現在内容、選択理由、重点、残件、次の読込先を更新する。継続して役立つ失敗はLESSONS、採否の背景はDECISIONS、実際の参照範囲はREFERENCE_LOGへまとめる。変更部分の意味と依存への影響、必要な検査結果と未実施範囲をCONTENT_HEALTHへ戻す。旧い次操作や無効な前提を本文へ残したまま、新しい説明を最後へ追記するだけにしない。過去の実施時点・コマンド・失敗証拠を現在値へ一括置換せず、現在の案内と区別する。

担当情報に変化がなければ更新不要の理由を示す。新しい結果があるのに会話要約だけで終えない。統合されるまで候補と明示し、途中チェックポイントを採用済みの正本にしない。

# 7. 更新・受け渡し・保存

## 7.1 基準と編集元

更新は開始コミットに対する追加・変更・削除・改名の集合として扱う。Codexの主担当はローカルの変更候補をまとめ、並列作業者は固定基準と限定した編集範囲の差分を返す。RPT-018/D-133により、Codexが限定した作業ブランチへの保存・PR作成を担当し、ユーザーがマージを判断する。操作はHTMLの現在入口が示す保存手順に先に記し、実施後の値と証拠を同じ手順へ戻して固定SHAで照合する。コードと必要な文書・台帳の更新を同じ変更として審査する。

ファイル名と役割は安定させる。日常は変更ファイルのみを渡し、構造を是正するときは配置全体への影響も確認する。ユーザーの保存した旧ZIPは消さず、現在ツリーへ再投入しない。

## 7.2 受領と保存を分離する

生成済み、ローカル検査済み、利用者受領、作業ブランチ保存、PR統合、統合後再取得、新スレッド復元を区別する。手元にファイルが存在することだけでリポジトリ反映を主張しない。

配布ZIPと検査記録はローカルの受け渡し物であり、毎回そのZIPをGitHubへアップロードしない。現行のファイル一覧はCONTENT_MAP、バイトの版固定はGitのtree/blob、ローカル配布のハッシュは配布側の記録で担当する。

## 7.3 旧配置の是正

**完了した0.3の配置是正の説明。現在の再実行指示ではない。** 実施済みの受入はHTML S06とVERSION_HISTORYに保持する。

最新の要求・構想・タスク・不確実性・判断・教訓の受入先を先に確認する。参照例はreferencesへ移し、現在の長期計画はdocsへ更新する。その後にだけlegacyと初回専用manifestを作業ブランチから削除する。内容マップに移行理由と受入先を示す。単なるフォルダー改名や無検討な削除で済ませない。

実操作はHTML S06。事前にC1固定ZIPをローカル退避し、追加・置換→旧パスの削除→PR審査→main再取得を行う。削除は作業ツリーの通常変更であり、Git履歴の消去はしない。

## 7.4 Projectと緊急復旧

S10-3で認めた一時的なAI探索資料・提供原本の掲載は第1.1節の境界に従う。原本3冊のGit保存・固定読戻しは完了しているが、Project側の削除を指示するものではない。以下の薄い入口はProjectを利用する際に正本の所在を示す規則であり、Projectの参考資料を禁止する意味ではない。

Projectを利用する場合、その開始指示には正本の場所と読む順序を保存する。過去添付が残る場合も最新情報として扱わない。Codexでは実際に読み込まれるAGENTSとREADMEから同じ担当文書へ進む。利用していないProjectの画面未確認を、Codexでのすべての作業を止める条件にしない。GitHub接続不能時には、ローカルの版付き保存からその版時点の開発を再開する。最新版である保証はしない。

過去実験の完全再実行に必要な大容量入力の保全は別の設計事項である。ローカルZIPがあるというだけで全実験入力が保存されたとは扱わない。

# 8. 検査機構と復旧試験

## 8.1 三段階の検査

| 段階 | 検査内容 | 実施時期 |
|:--|:--|:--|
| 軽量検査 | JSON/CSV構造、参照ID、対象版、変更対象、ファイル存在、単位・型、短い単体試験 | 各変更の終了時 |
| 統合検査 | 固定気象入力での実行、契約試験、回帰比較、関連文書の再生成、公開APIと構造ガイドの照合 | 統合前・統合後 |
| 配布／復旧検査 | 全対象のハッシュ、ZIP展開、依存情報、PDF視認性、新規環境でのビルド、会話なしの再開 | 正式配布・節目 |

ハッシュはバイト同一性を調べる。マニフェストの内容が不足していないこと、資料の意味が正しいこと、世界により新しい版がないことまでは証明しない。新旧PDFの意味やモデルの正しさには別のレビューが必要である。改ざんまで脅威に含める場合は、別途信頼された場所のダイジェストや署名を検討する。

マニフェスト自身とそのダイジェストは、自分の内容ハッシュ一覧から除外する。マニフェストが参照するsource_commitは生成元のコード版とし、そのマニフェストを含む将来のコミットIDを同時に埋め込もうとしない。

## 8.2 復旧試験の合格条件

会話を見ない新しい担当者・新スレッドが、配布物だけから目的、現在状態、未決事項、次のタスク、判断理由、正本への経路を説明できることを確認する。開発が始まった後は、必要ソースの取得・展開、依存環境の構築、固定入力の実行、関連PDFの再生成まで行う。

正常系だけでなく、ファイル一つの欠落、PDFだけ旧版、同じ論理IDの重複、改変バイト、適用元の違う差分、削除済みの古い資料の残存を意図的に作り、検出されることを試験する。現在のcheck_stateは、パスの不足・余剰、禁止された旧配置、本文状態・参照整合などに限定する。配布のハッシュ照合は別のローカル検査記録で行う。将来の差分適用器や意味レビューまで実装済みとは扱わない。

立上げのG0〜G2には、利用者側の受領、保存、現行mainからの新スレッド復元が必要。ユーザー環境のPDF再生成や本体テスト等は後続の別ゲートであり、緊急の引継ぎを止めない。G0〜G2成功をP0全体の完了とも取り違えない。

# 10. シミュレーター開発の骨格と段階計画

## 10.1 最初に安定させたい境界

初期本体はD-154でPythonを採用した。既存の科学計算資産と検証のしやすさを活かし、性能が問題になった箇所は測定して判断する。0.20のweather/dynamics/cliという大括りだけでは、独立に変わる責務が集中した。0.24の修復では、次の意味の境界から実体を分ける。名称やファイル数を先に増やすことは目的ではない。

`取得・キャッシュ → 正規化された環境場 → 飛行モデルとイベント → 数値積分 → 結果・評価 → 表示／出力`

環境場の問い合わせ契約では、時刻、位置、高さの種類、気圧、温度、風、必要な熱入力、品質・範囲外フラグを明示する。提供元が違っても同じ契約を満たすようにする。物理モデルには必要入力と適用範囲を宣言させ、入力不足のまま静かに別モデルへ落とさない。

簡易運動学モデルと、速度や熱状態を積分するモデルは状態量が異なり得る。共通にするのは設定の検証、環境参照、イベント契約、出力の意味であり、すべてをTawhiriと同じ小さな状態ベクトルへ無理に押し込めない。逆に高度化を理由に、検証に使う単純モデルを削除しない。

この流れはデータの受渡しを示し、そのままimportの方向を意味しない。環境の取得側は製品固有の配信・単位・復号を持ち、連続場は保存データから照会を返す。物理は環境の値を使い、単一飛行は選択した物理とイベントを数値解法へ接続する。数値演算は気球やデータ提供元を知らず、結果表示は保存結果から作る。設定・来歴・品質情報の横の依存も構造ガイドへ示す。

一般的な数値積分・誤差制御・根探索は既存ライブラリへ委譲する。0.24のD-163ではSciPyのRK45とbrentqへ移し、構造移行の同値比較と、数値移行の許容誤差比較を分ける。支持端・相切替・状態別誤差・途中結果はこのプロジェクトの契約として明示する。旧RK4は比較元であり、実行経路として維持しない。性能優位は実測せず断定しない。後に状態や剛性が変わるモデルを追加するときは、その要請からsolverと誤差を再検討する。

縦の分解と同じ階層の横の連携を、理論のドメインと依存関係に沿って設計する。階層数やクラス継承の多さが目的ではない。構造ガイドのモジュールと主要機能の索引から、理論・主要入力/出力・呼出元・利用先・検査・変更時点へ辿れる粒度を選ぶ。管理対象が把握できない分割は設計の再検討対象である。

## 10.3 精度改善の主張を切り分ける

気象データの変更と物理モデルの変更は別に評価し、比較可能な場合は基準／変更気象と基準／変更モデルの組合せを揃える。同じ入力が物理的に意味を持つかを確認し、条件を揃えられない公開API結果を厳密な基準値にはしない。

式を正しく実装したこと、現実との整合が確認できたこと、不確実性の大きさを説明できること、利用者と開発者にとって使いやすいことを別の問いにする。数値の極限・収束・再現・無効入力は検査で調べ、モデルの妥当性はその条件に使える手元記録・公開実験・研究知見から評価する。原記録の意味が不明な値を、無条件に真値や校正値へ変えない。

比較候補の受入、標準設定への採用、実飛行の精度改善主張は分ける。予測の良否を判断する場合は、経路・高度・時刻・着地・計算時間・予測域などから、その目的に必要な量と条件を選ぶ。上昇だけの比較を着地点改善率へ広げない。任意に置いた感度幅、モデル間の差、条件付きの確率分布、観測で校正された予測域を混ぜない。

当時の予報能力を評価する入力は、その時点で利用可能だった情報に限定する。再解析による事後条件分析や、観測から途中更新した計算は別の評価である。調整と評価の分離を図るが、粗い少数記録しかない場合は支持できる主張を限定し、追加実験を必須としない。定量指標だけで総合的な良さを定義せず、選択肢の絞り方、説明の理解可能性、性能・拡張性・操作性を継続してレビューする。

### 目指す利用の姿と、風資料から得る設計上の意味

目指すのは、打上げ日時と機体を入力して一本の軌道を得るだけでなく、企画段階の季節・場所選定から、予報が届く期間の予定調整、当日までの更新、飛行後の検討まで、根拠をたどって判断できるシミュレーターである。利用者は落下集合を見て候補を絞り、違いが大きければ高度別の風や滞在時間へ戻り、必要ならモデルの仮定を変えて判断の頑健さを調べる。日本の任意地点、無償・特別資格不要、追加実験なし、等温初期モデルと後続拡張という既決方針の下で、この一連の行為を支える。

提供風資料の良さは、図が多いことより、問いを答えが出る形へ変えている点にある。PDF p19–24は「季節差があるか」から「どこまで細かい時期を区別できるか」へ問いを絞り、年を分けた検証、同じ年における候補間の差、差が小さい場合の粗い粒度の選択までつなぐ。p88の比較は、時刻固定と位置固定の効果を別の軸にする。図表はその比較を読者が判定するために選ばれている。これを本開発へ適用する際も、半月という幅や報告された改善率を移すのではなく、目的・対象集合・比較条件・判定・次の行動をつなぐ考え方を受け入れる。原資料の数値検証の限界はWIND_REPORT_REVIEWに残す。

S33/D-164で置く以下の構想は、その目的から推測した設計仮説である。今の一飛行核を活かす一方、製品やモデルを追加すれば自然に分析システムになるとは考えない。小さい異なる用途を通し、共通にできる境界と分けるべき意味を確かめて改訂する。

|:--|:--|:--|
| 季節・場所候補をどう絞るか | 機体とモデルを固定し、過去の年・時期・候補地点を変える。次に同じ過去場でモデルを変える | 同じ尺度の場所/時期別落下集合、距離・方位の要約、標本数と停止内訳。モデルで候補の見え方が変わるか |
| 新しい予報で判断は変わったか | 同じ打上げ条件・モデルの下で予報runを更新する | 対応する条件の落下集合と差。どの気層の変化が差に寄与したか |
| 打上げを延期するとどう変わるか | 一つの予報runと機体・モデルを固定し、打上げ時刻を変える | 時刻候補を並べた落下集合、移動方向/距離、飛行時間。予報更新による差と混ぜない |
| どの仮定・過程が結果を動かすか | 同じ気象・機体実現値に対してモデルを対応付ける | 上昇/下降別の滞在時間と移流、対になった着地点差。効果の符号と相殺を保持 |
| どこまで結果を信頼できるか | 当時利用できた予報、事後再解析、使える観測区間を識別する | 条件を揃えた誤差・欠測・比較不能区間。何の能力を評価した値かを明示 |

過去場のばらつきは選んだ年・季節の気象条件の違いであり、当日予報の条件付き誤差とは異なる。予報member、機体の実現値、モデルの選択も別の軸である。各標本には何を固定し何を変えたかを残し、モデルの和集合を根拠のない確率混合にしない。各時空間点で独立に風を振る方法では、場のつながりを保持したことにならない。

平均落下点だけでは逆方向の標本を相殺し得るため、点群・方向・分位点を目的に応じて組み合わせる。海への到達を判断するには、地面高度だけでなく海陸区分と未判定の扱いが要る。図の共通尺度、集計した母数、停止標本を同時に示し、取得領域から外れた標本を落として好ましい分散に見せない。すべての図を常時並べるのでなく、候補を絞る図から理由を調べる図へ進める構成とする。

### 用途から必要になる責務と、0.25時点の実装の位置

### 将来費用から、今の境界を疑う

現 `load_weather` は常にGFS規則付きの場を構築する。JRAのデータを復号できても、保存入口・時刻規則・地表量・品質が同じ意味で接続されなければ本体で使えない。製品を識別して正しい場を作る責務と共通照会を分け、GFS時刻を削って検査を通すような代用をしない。共通の照会があることと、すべての製品を一つの保存形式へ押し込むことも別である。

現保存場はJSON全量を読み、配列を検査してメモリへ置く。出力は一飛行ごとに7ファイルを作り、気象入力とコードの指紋を読み直す。例えば2016–2025年を6時間ごとの14,612起点、3地点、2モデルで計算すると87,672飛行、同じ出力方式では613,704ファイルになる。41×41格子・33圧力面・上空5量/地表6量を倍精度で持つ机上例では、4時刻の数値だけで約9.2MB、全14,612時刻なら約33.6GBとなる。これは要件でも性能実測でもなく、JSONやPythonの保持・変換費用を含まない規模例である。

この見積りだけでも、場の用意、個別結果、集計、読者へ渡す資料を同じ寿命にする構成には疑いが生じる。原本と変換済み場を共有し、個別結果を再開可能に保持し、必要な集計と代表例だけを表示へ展開する方向を検討する。分割読込、保管形式、並列化等は取得・復号・読込・飛行・保存を分けて測ってから選ぶ。先に巨大な基盤を作るのでなく、後で分離できない保存契約を今増やさないことが重要である。

細密DEMの導入も接地高度の差替えだけでは済まない。気象場はモデル地形から地表付近を再構成するため、DEM上の位置が気象の支持外になる場合がある。接地に使う地表と、気象再構成に使う地表を区別し、その間の支持・近似・欠測を扱う必要がある。熱/慣性を追加する際には、現在の固定3状態に対して初期化、相の引継ぎ、許容誤差、結果と診断も変わる。こうした変更範囲を今把握し、任意状態の枠組みだけを先行実装することは避ける。

### 0.25で提案した小比較と、その適用位置

**0.26での位置づけ変更：** 以下はD-164で出した技術検証案として保持する。RPT-043/D-165では完成像の具体化が先であり、16飛行・2地点・2季節を次の主成果や製品要件に固定しない。第10.6節とSIMULATOR_VISIONから利用価値と不足を吟味し、その後に適切な試験規模を選ぶ。

最初の候補は、**同じ機体・モデルの下で季節・場所候補をどう絞り、その判断がモデル選択に依存するか**を調べる小分析である。まず、候補地点/時期を並べた出力案、固定条件と比較軸、標本の選び方、停止を含む母数、何をもって次の調査へ進むかを具体化する。少数の過去瞬時場を取得して全飛行へ渡し、落下集合と原因をたどれる表・図まで通す。少数例は分析の構造を確かめるためであり、季節や場所の優劣を結論する標本ではない。異なる製品を一件ずつ飛ばすだけで、この問いへ答えたことにはしない。

設計を試す最小案は、既存例に対応する北海道/和歌山の2地点と冬/夏の2時期について、各組で異なる年から1起点ずつ計2起点を選ぶ8気象ケースを、簡易/等温の2モデルで解く16飛行である。同じ時期の起点は地点間でも揃え、同一の気象標本をモデル間で共有し、取得時刻の間にある打上げ時刻も含める。既存の地点例を使うことは、地域ごとに異なる機体設定を流用することではない。共通の機体条件と破裂条件を揃え、簡易モデルの規定速度など固有の設定値は対応表に選定理由を残す。固有値の対応が未定のまま、設定の違いも含む結果差をモデル式だけの効果と呼ばない。

これは実飛行計画でも統計推定の必要標本数でもない。まずJRA/ERAのどちらで必要量と全飛行の支持を小費用で揃えられるかを具体的な取得計画で比べる。領域・飛行中の時間幅・上端の数値試行余裕を含め、16という数に合わせて支持を切り詰めない。

例えば最初の図は、候補地点と時期を行列に並べ、同じ尺度でモデル別の着地点を示すものが考えられる。横に完了数・停止理由・距離と方位の表を置けば、「近いように見えるのは強風例が停止したためか」を確かめられる。モデルで見え方が変わる組だけを次の図へ取り出し、同じ気象標本に対する高度滞在と移流の差を示す。この順序なら、すべての軌道を一枚に重ねるよりも、候補の違いとその理由を追いやすい。実際の標本で差が読み取れなければ図や問いを改め、見栄えのためだけに結論を作らない。

次に、多年度へ増やす前に標本の期間・時刻・地点の対応と費用を測る。時期の粒度を細かくする場合は、独立に近い年/期間を分けた評価と候補間の対応する差を用い、差を支持できないときに弱い主張へ戻れるようにする。原資料の半月区分を全国の固定値とせず、どの程度の標本で何を区別できるかをその対象から判断する。

予報更新と延期は、同じ打上げ条件でrunを変える例と、一つのrunで打上げ時刻を変える例を分けて作る。過去分析と同じ照会・一飛行核・結果識別を使えるかを確かめ、共有できない意味があれば設計を修正する。気象memberの取得調査も進めるが、GEFS等の採用や分散実装だけを自動的に次の主成果にしない。

既存15便の原セル・単位・時刻・比較可能な区間の整理と、必要な取得経路の費用調査は並行できる。Codexが小分析、図表、未確定部分、費用の材料を作り、人間には候補を絞るうえで重視する条件や大きな代償を伴う選択を具体的に求める。実装が増えるたび、図から判断へ進めるか、構造ガイドから変更先と影響先へたどれるかを実物で再評価する。

# 11. 計算の再現情報と保守

一つの計算には、設定の完全展開値、設定スキーマ版、コード版、未コミット差分の有無と必要な差分、依存環境、ソルバと許容誤差、乱数の生成方法とseed、実行条件、気象データの初期時刻・有効時刻・取得時刻・範囲・変数・ハッシュ、地形版、警告、終了理由、出力スキーマ版を保存する。

数値的に許容範囲で一致する再現と、ファイルのバイト列が一致する再現は異なる。PDFの生成時刻やライブラリ差の扱いを決め、必要以上にバイト同一性へ依存しない。一方、気象入力を「latest」のまま再取得して同じ実験を名乗らない。並列化した乱数実験では、作業順が変わっても同じケースの乱数系列を再構成できるようにする。

データ取得の統合試験と、ネットワーク不要の物理・回帰試験を分ける。提供元の停止や仕様変更で物理コードの単体試験まで停止しないようにする。キャッシュの再利用条件にはデータだけでなく変換処理・単位・補間仕様の版を含める。

公開前には、研究用予測と実際の運用判断の境界を文書にする。規制適合や飛行の安全をシミュレーターの合格だけで保証しない。具体的な飛行運用を対象にする時点で、別の調査・受入タスクを立てる。
