# 意図を読み取り、判断と成果を継続させる開発規範

[更新:0.23.0] [確認:0.24.0] — CONTROL / REV-230-PRINCIPLE

この文書の基礎は、情報を総合して意図を推測し、その解釈・設計・成果を意図に照らして問い直すDC-JUDGMENTである。調査、議論、実装、資料、検査、管理、分担、引継ぎを含むすべての作業に適用する。以下の個別契約は、その原則を判断・行動・記録として継続させるための具体化である。
過去の14契約は以下の5つの問いに配置されている。今回その内容を保ち、共通の基礎と各工程を接続する。DC-IDを参照先に使い、掲載順の章番号へ依存しない。

| 枝 | ここで決めること | 次の枝へ渡す結論 |
|---|---|---|
| A 状態の境界 | 何が正本で、各実体をなぜ残すか | 意味・立場が判明した対象集合 |
| B 読み方と点検 | 今回どの範囲を読むべきか | 根拠付きの現状と未確認範囲 |
| C 説明の設計 | 細部が全体の問いにどう寄与するか | 情報を落とさない論証構造 |
| D 改訂の記録 | 変更理由と前後の内容をどう対応させるか | 追跡可能な変更と検査証拠 |
| E 実行と限界 | 合格は何を保証し、どこで止めるか | 次の担当が越えてはいけない境界 |

単なる目次ではない。各枝の結論が後段の前提になり、枝内でも同じ問い・根拠・検討・結論を組み立てる。管理JSONの欄が埋まるだけで説明が良いと判定しない。

## DC-JUDGMENT — あらゆる作業を支える判断原則

<a id="DC-JUDGMENT"></a>

### 原則と、その必要性

良い仕事は、記載された項目を充足するだけでは成立しない。要求の本質は一文に収まらず、複数の指示、資料、既決事項、実物、利用状況の関係から読み取る必要がある。**情報を総合して本質・ニーズを推測し、状況と人間の立場からその推測を問い直し、具体的な計画・設計へ結び付け、案が当初の意図に合うかを全体として判断し、実施し、その結果を再び自己評価する。** これを全作業の共通原則とする。個別の失敗例から作った対策集ではなく、まだ例のない仕事にも、その都度解釈して適用する上位原則である。

この関係は一方向の固定手順ではない。設計・調査・実施・評価で新しい事実や違和感が得られたら、必要なところまで戻る。作業の各部分にも適用し、最後には部分の結果を全体へ戻す。名称、段階数、様式を揃えることを原則の履行と取り違えない。

### 意図を推測し、推測自体を疑う

主担当は、誰がどの状況で何を理解・判断・変更・実行できるようになるべきかを、関連する情報を結んで捉える。求められたファイル名や作業名は手段であり、その用途を考える。書いていない必要まで推測する責任を持ち、明記された事実・制約、そこからの解釈、まだ決められないことを区別する。

推測を一度得ただけで確定しない。利用する人の知識・注意・負担、仕事の自然な流れ、分野の慣行、前後の作業、長期方向に照らして無理がないか、別の解釈なら何が変わるかを問い直す。「人間なら当然」という直感も有力な手掛かりだが、状況に依存する仮説であり、明示要求を上書きする根拠にはしない。未取得の記載・数値・実施結果を事実として補うことや、推測から操作権限を作ることは禁止する。

調査で解ける不足はCodexが調べる。既決事項や通常の利用を踏まえて推測できる部分は、理由と見直す条件を持って進める。ユーザーにしか決められず、解釈によって目的や大きな代償が変わる部分だけは、具体案と比較材料を用意して問う。推測の不確かさを、毎回の承認待ちや技術調査の丸投げへ変えない。

### 案と成果を、全体の意図へ戻して判断する

設計前に捉えた意図を戻り先として、責務、関係、順序、表現、道具、作業範囲を選ぶ。既存の配置や前回の手段も、その用途を満たすかを問い直す対象である。案を具体的な利用・読解・変更の場面に置き、利用する立場から全体として自然に役立つかを見る。その後に必要な細部を調べ、再び全体へ戻る。確認する場面は今回の意図から選び、過去の例や固定の項目群を万能な試験へしない。

全体の分かりやすさ、調和、過不足、扱いやすさには、細部へ分解した条件だけでは判定できないものがある。通読・視認・操作・変更の想定など、その成果物に合う形で実物へ接し、説明文ではなく案や成果そのものから評価する。全体に違和感が残るなら、項目の充足や試験成功で打ち消さず、その箇所と状況を捉え直す。理由を完全に言語化できるまで判断を禁止することも、単に「自然」「良い」と言って済ませることもしない。判断に効いた具体的な観察と、その限界を伝えられる範囲で残す。

実施中に前提や案との食い違いが判明したときは、局所的なつじつま合わせの前に、目的の解釈または設計を見直す。初期の解釈に固執せず、新情報・観察だけでなく、同じ情報を結び直して誤読や不足に気づいた場合も理解を更新する。旧解釈、再検討した材料、変更理由を残し、元の要求と理由付きで更新した解釈を評価の戻り先にする。でき上がったものを合格にするために、開始時の意図や受入の意味を黙って縮めない。

### 継続できる仕組みとして適用する

原則本文の編集元は本節だけとする。個別作業では、原則を今回どう解釈し、どの選択へ結び付けたかを既存の担当資料へ記す。原則の全文や内部の思考過程を毎回複写せず、判断を再開できる結論・根拠・未確定を残す。

| 作業上の接点 | そこで行う判断と、残す場所 |
|---|---|
| 開始・継続・再開 | README/DC-STARTから本節を適用する。既存の目的と今回の情報を結び、今回の意図・推測の根拠・不確かな点をHTMLの対象手順または設計を担当する本文へ置く。継続時はその所在と変わった点を確認し、作り直さない |
| 計画・設計から実施へ | WORK_ORDERの目的と受入、または担当設計の既存欄で、なぜこの案が意図を満たすと判断したかを示す。機械検査と全体の適合判断を区別する。重大な不一致は案へ戻し、依存しない作業は進める |
| 実施中の発見 | 調査結果・失敗・違和感が解釈や設計を変える場合、担当本文と採否の記録へ戻す。細かな一操作ごとに新規議事録を要求しない |
| 分担と統合 | 主担当は全体の意図、子担当の役割、既決制約、疑うべき前提を渡す。分担者は局所成果と全体への懸念を返す。主担当が統合物を当初の意図から評価し、部分の合格の和で代替しない |
| 終了と引継ぎ | DC-CLOSEで実物と開始時の意図を照合し、得られた効用、不一致、未確認、次に戻る判断を実施欄へ残す。会話なしに意図・現状・次の問いへ戻れるようにする |
| 仕組み自体の見直し | 意図の説明を人間へ繰り返し求める、同じずれが再発する、記録負荷が判断を圧迫する等の実績が出たら、本原則の適用方法も問い直す。項目追加で覆わず、抜けた関係と不要な重複を見直す |

すべての作業で原則を適用するが、説明量と手段は判断の難しさ・影響・不確かさに合わせる。既存設計に収まる小変更では、既存の意図への参照と今回の差・結果の短い説明でよい。これは適用の免除ではない。会話で答えるだけの作業でも判断を行い、開発上の決定や状態が変われば既存の記録先へ戻す。新しい判断台帳、毎回同じ段階別作文、全件の人間承認を追加することを仕組み化としない。

**判断の責任と限界：**主担当が適合の総合判断を担う。影響や不確かさが大きい場合の独立読取は、記録欄の充足でなく意図の推測と案の前提も問い直す。機械検査は根拠・所在・整合の補助であり、本質の理解、自然さ、将来の遵守を真偽値や点数で認定しない。原則の導入、個別作業への適用、その成果の適切さ、継続運用での有効性は別々に評価する。

### DC-TIME — 責務と時間の意味

<a id="DC-TIME"></a>

**問い：**時系列をどう同定するか。**根拠：**候補とGit保存・再取得は異なる事実。

VERSION_HISTORY.jsonは版要約とGitの観測済み遷移の編集元。CONTENT_HEALTH.jsonは現在の範囲・焦点・再確認の証拠の編集元。HTMLの実行状態をJSONに二重入力しない。過去の実ファイルはPCへ退避し、これらの簡潔な索引だけは現在の判断・整合確認に必要な状態として保持する。

`version_order`は比較に使う版の順序である。0.9から0.10を小数として計算しない。一つの版に作業コミット、削除コミット、マージ、後続の試験コミットがあり得る。作業ブランチ先端とmainへの統合コミットを区別する。分岐はparents配列で表し、一直線の偽の履歴にしない。

`review.on`と期限判定の基準日はUTCとする（check_healthの実装に対応）。文書表紙の`as_of`と利用者報告の表示日は日本時間の場合があるため、同じ「日付」として無条件に比較しない。旧版の当該確認は日本時間2026-09-19未明／UTC2026-09-18に行った。未来日エラーを消すために過去日を偽装せず、実際の確認日時と基準を記録する。

候補に将来の統合SHAは書けない。候補のintegrated_commitはnullとし、実際の統合後に取得したSHA/親/tree/PRで確定する。記録そのものの保存SHAを再帰的に本文へ書く必要はない。次の意味ある更新で、前回観測の統合を索引へ記録する。新スレッドは索引の古い観測値を最新HEADと取り違えない。

**この部分の結論：**現在の版と採否を別々に復元できる。

### DC-SCOPE — 統一マーカーと範囲の継承

<a id="DC-SCOPE"></a>

**問い：**変更と確認をどう分離するか。**根拠：**部分更新では親子の時点が異なり得る。

人が読む可変本文では `[更新:0.4.0] [確認:0.4.0]` を用いる。未確認なら `[確認:未確認]`。間に別の文字を挟まず、この書式で検索できるようにする。更新とは意味または挙動の変更で、単なる再読・確認印の更新とは異なる。確認は登録した目的・依存先に照らしたレビューであり、実行していないUIや科学モデルまで保証しない。

HTMLは見出し直後、MDは文書冒頭または特別に管理する節の見出し直後に置く。必要な場合は子範囲にだけ上書き印を置く。範囲のID・抽出先・parent・updated_in/reviewed_inはCONTENT_HEALTHに対応づける。値nullは親から継承する。**子の内容更新で親や兄弟の最終更新を勝手に新しくしない。** 親の指紋は登録された子範囲を除く自身の本文を対象にする。

初回はHTMLを節/小手順単位、それ以外を文書単位とする。表の行や理論の枝は必要になったら範囲を分割できる。生成物・既存の未改変参考資料・CSV/JSON/コードの版はまず登録簿で明示し、無関係な資料へ今回の確認印を一括で埋めない。古い資料に範囲内マーカーがない場合は登録簿のdefaultが適用され、その本文を次に変更したときにマーカーも導入する。

`revision`はファイル自体の編集版であり、プロジェクトの全ファイルが同じ値である必要はない。変更していない計画MD/TeX/PDFを0.4と偽装しない。削除した範囲は現行レジストリから除去し、参照・焦点・依存・索引を同じ変更で修正する。削除理由が今に効く場合だけ判断記録に残す。

**この部分の結論：**確認した範囲だけを新しい証拠に結ぶ。

#### S10-3から具体化した契約

PLANの部分改訂では、変更する既存章と表紙メタデータを子範囲として切り出し、その本文・前提・限界だけを確認する。旧版にも同じ一意の見出し境界を適用し、親から子を除いた残部が変わらないことを比較する。子範囲の追加は構造変更として前後と理由を記録する。親PLANの未確認を子の確認やPDF再生成で消さない。

### DC-RETENTION — 版の再取得と独立退避（見直し案）

<a id="DC-RETENTION"></a>

**問い：**何を保管し何を整理できるか。**根拠：**Git履歴と独立退避・固有資料は別である。

現行ファイルの版管理はGit、障害時の開発継続は確認済みの独立したツリー退避、Gitにない報告・配布外枠・未コミット変更は別保管、と責務を分ける。毎コミットの事前ZIPを恒久義務にしない。当面の提案は最新と直前の2つの確認済み節目。全履歴のオフライン保証や節目後の無損失保証ではない。

具体的な版別整理表と操作はHTML retentionのRET-01〜05を唯一の実行案内にする。削除できるのは代替を確認し、固有情報を含まない重複と判断したファイルだけ。利用者のPCの保管一覧は未取得なので全ファイル削除可とはしない。整理自体をS09合格の前提にしない。GitHub履歴・権限・公開範囲は変更しない。

S09完了は、S08合格が入った版の統合、同じ版のAI再取得、利用者のPC退避・展開確認を合わせて判定する。RECEIPT-060はrepo外で実際の統合SHAと受領結果を持つ。保存前のHTMLに自分の保存完了を書き込む循環を要求しない。次の通常開発改訂へ最終実績を戻し、管理だけの再改訂を強制しない。

検査はS09の操作5欄とRET規則の欠落、S08完了時の8観点/利用者照合根拠を検出する。現物のPCバックアップ可読性や削除安全性は自動証明しない。元の科学・外部出典の未確認8範囲と初回期限は維持する。公式の技術条件はHTML SRC-09/14/15/16。

**この部分の結論：**履歴の全ZIP化を避けて根拠を失わない。
0.10.0で当該8範囲のうち生成・登録の5範囲を実際に点検する。初回未確認として残るのはPLAN残部と参考PDF/TEXの3範囲であり、科学的未確認はU-014等にも保持する。過去の「8範囲」は当時の未確認数で、現在の確認を証明する数字ではない。

### DC-ASSET — 実体を用途不明のまま残さない

<a id="DC-ASSET"></a>
`CONTINUITY_CONTRACT.json`を**必要性・立ち位置・退役条件**の編集元とする。既存CONTENT_HEALTHは時点と範囲の編集元であり代替しない。全実在パスを突き合わせ、用途不明な登録、使用先不明なプログラム、生成元のない派生物を拒否する。CONTENT_MAPの役割表はJSONからの表示であって第二の原本ではない。

退役判断は「使っていなそう」ではなく、使用先・必要性の消失・代替の受入・固有証拠の有無を調べる。削除を実行する前に、元の意味が必要なところへ移ったことを確認する。テストも、守る契約が有効なら失敗修正後も必要である。退役候補というラベルは削除権限ではない。

Git外の成果物はexternal_artifactsで種類ごとの生成元・保管・再生成・欠落時の扱いを定める。利用者PC全体を走査したと主張しない。今回見えている配布外枠、報告、検査ログ、訂正補遺を例として登録する。作業用スクリプトが再開・再生成に必要なら、仮ファイル扱いせず、正式な手順かツールへ昇格する。使い捨て再現試験の発見はLESSONSと回帰テストへ受け入れ、元の一時フォルダーを通常復旧の前提にしない。

#### S10-3から具体化した契約

本体では、モジュールと主要機能を担う関数を基本の管理粒度にする。公開API、計算に影響する設定・データ変換、テストも、意味と利用先を説明できる対象として含める。すべての小関数へ同じ分量の説明を強制するのではなく、管理対象が把握可能になるようにモジュールを設計する。

構造ガイドの各対象には、**識別子と所在、役割と存在理由、上流入力と下流出力、理論・単位・仮定、依存先と利用先、検査との対応、導入・意味変更・再確認の開発時点、現役性**を持たせる。以下は本体実装で満たす記録契約である。本契約の初導入時には索引の具体形式・自動検出をT-007の未実装事項として残した。0.20で主要APIと試験の索引/実AST署名照合を導入し、0.21ではIMPLEMENTATION_INDEXに実ファイルと関数の階層・静的依存を追加した。所在の機械照合と責務/意味の人による読解を分け、将来APIや科学的妥当性の自動検証を実装済みとはしない。

| 欄 | 決めること | 混同を避けること |
|---|---|---|
| 識別子／所在／主要機能 | モジュールと主要機能へ戻れる一意な案内 | 名前の似た別関数、過去版の同名パス |
| 役割／存在理由／位置 | どの問いを解き、全体へ何を渡すか | ファイルがあることを必要性の説明にしない |
| 理論対応／単位／仮定 | 式・入出力・適用範囲・実装の対応 | コメントへ式を複写するだけで一致としない |
| 依存先／利用先／影響先 | 呼出、設定・データ形式、意味・理論上の前提を種別付きで記録 | import一覧を全依存としない |
| 対応する検査 | 守る契約、検査入力、何を検出するか | テストがあることを科学的妥当性としない |
| 導入／整備／確認の時点 | 版と実際の基準SHA、確認した範囲・証拠 | タイムスタンプだけでレビューしたとしない |
| 現役性／残存理由 | 現役、非現役の残存、退役の判断 | 古いもの＝非現役とはしない |
| 残存の次判定 | 理由・リスク・次の開発節目・判定担当・選択肢 | 「当面残す」だけで終えない |

非現役を残す場合は、短すぎる形式的な繰返しでも、無期限でもない開発上の節目をその場で定める。固定日数や改版数を根拠なく一律に採用しない。次の判定では、削除、理由を更新して残存、現役へ復帰を選ぶ。再び残すなら同じ手続きを繰り返す。削除には使用先・代替・固有の証拠を確認し、許可された変更集合で実施する。

現在の比較に必要な単純モデルと、現在の契約を守る回帰試験は現役である。逆に、用途不明の実体をただ「念のため」に保存し続けない。用途未確定なら所在・由来・利用先と判定ゲートを課題にし、勝手に削除もしない。

### DC-INDEX — 軽い探索索引と、検証入力の扱い

<a id="DC-INDEX"></a>

**問い：**索引を本文の代わりにしないには。**根拠：**索引は派生物であり検証入力にも例外がある。

**この部分の結論：**軽い探索と必要な実取得を両立する。

<a id="DC-FRACTAL"></a>
#### 小さな単位：何を答える段落・節なのか
各単位は**問いと動機 → 必要な前提・背景 → 根拠を結ぶ説明・導出 → 結論・適用限界**を持つ。毎段落に同じ小見出しを強制するという意味ではない。読み手が一度に追える範囲で一つの推論を閉じる。単なるラベルや一行の説明で、必要な導出・具体例・条件を置換しない。

#### 上位の単位：その結論で何が分かるのか
複数の節を並べる理由と順序を明記する。独立した選択肢の比較なら横に並べ、前提が必要な説明なら順序づける。子の結論を親の主張に戻し、そこで何が解け、何が残るかを示す。図、式、API表、例にも「どの問いの根拠か」を持たせる。

#### 実例：検査用の三層はなぜ別なのか
「全部okなら安全」という主張では、未知のファイルや自己申告の誤りを見落とす。そこで、第一にcheck_stateがファイル・本文表示・局所リンクを調べる。第二にcheck_healthが確認時点・範囲・依存指紋と期限を調べる。第三にcheck_contractが用途・寿命・論証単位と変更理由の対応を調べる。この結論を実行の枝へ渡し、run_checksはそれらの実行結果を保存する。保存したことは正しさの追加証明ではなく、失敗を後から判断できる条件である。逆引きはCONTENT_MAPの「管理ツールの構造」を読む。

#### 設計図と本文の相互点検
各資料の主張、必要内容の一覧、親子の寄与、順序の理由、未説明の範囲を登録する。本書とCONTENT_MAPに加え、執筆した本体の理論/構造/操作/実装詳細もnarrative_unitsで管理する。既存PLANは章の所在・役割の棚卸しまでで、全文の論証・科学出典の受入ではない。構造ガイド・理論ガイドは執筆開始時から同じ設計図を用い、変更時に旧固有情報の受入先と実装への忠実性を照合する。

レビューでは本文から主張を拾い直し、設計図にあって本文にない内容と、本文にあるが意図不明な内容の双方を列挙する。文字数や見出し数だけでは合格しない。参考Program_GuideのPDF2・3・14ページにある階層反復と逆引きの型は参考であり、ロケットの実装を気球へ採用する根拠ではない。

#### S10-3から具体化した契約

選定には、今回の問い、候補、比較条件、根拠、採否、代償、再検討条件を残す。情報をすべて同じ重みで羅列すること、結論だけに削減することの双方を避ける。性能・可読性・拡張性の衝突があれば、測定または理由と、その判断を見直す条件を示す。未知の性能値や外部研究の適合を推定で埋めない。

<!-- LOGIC:DC-FRACTAL:END -->

**この枝の結論：**この枝の成果は、本文と対になった内容・意図・順序・結論の設計図である。設計図を省略したまま見出しだけ整えて合格にしない。

### DC-CLOSE — 実施証拠と検査：DC-CLOSE

<a id="DC-CLOSE"></a>

**問い：**変更結果をどう状態へ戻すか。**根拠：**改版した本文とレビュー証拠が分離している。

まずDC-JUDGMENTにより、実物を開始時の意図へ戻して全体として自己評価する。何が利用者の行為を支え、どこが不自然・不足・未確認か、その判断に効いた観察を実施欄へ残す。試験結果と分け、意図の解釈を変えたなら理由を記す。以下の整合確認だけを完了条件にしない。次担当へ意図・推測の不確かさ・設計理由・残る判断の所在を渡す。

1. 更新した範囲に現在版の更新印を付ける。内容が変わらない範囲の印は保持する。
2. 実際にレビューした範囲について、目的に対応する結果、対象SHAまたは候補基準、日付、確認範囲、未検証部分をevidenceへ記録する。各範囲のreviewにはその時点の本文指紋と依存先指紋を結びつける。記録なしに確認版だけ繰り上げない。
3. 継承印を解決して、本文印と登録値、存在する範囲、版順、過去→現在の関係を検査する。CONTENT_HEALTH自身は自己ハッシュを持たず、配布物の外側ハッシュと差分レビューで保護する。
4. `python tools/check_health.py . --base <変更前の展開フォルダー>` を実行する。基準差分があるのに更新版を上げない、本文/依存が前の確認から変わった、期限切れ、新規範囲未確認、焦点漏れを失敗として検出する。`--base`未指定では変更印の基準比較は未実施と表示する。
5. `python tools/check_state.py .`、回帰試験、変更した生成物の再生成と視認性確認を実行する。ユーザーPCへPython導入を要求するのではなく、実行可能な作業者が担当する。実行不能時は同じ規則の手動確認と未実行を記録し、機械試験成功を名乗らない。
6. 未解決の点検対象を消さず、次の焦点と参照ログを更新する。日常差分は変更/追加/削除の集合と基準SHA、節目には全現在状態のZIPをPCに保持する。

`python tools/check_contract.py . --transition --base <固定変更前一式>`も実行し、用途・論証・変更理由の対応を確認する。比較未実施の通常検査を遷移合格にしない。固定された旧版の検査器から候補を点検する場合は、その旧版のtools/check_contract.pyへ候補rootと--baseを渡す。`--views`の出力でCONTENT_MAPのASSET_VIEWだけを更新する。JSONが編集元であり、表を独立編集しない。初回登録以後は、変更前の実体に対応する理由記録なしで合格にしない。

検査器は**記録と指紋の整合、必要なレビューの未実施**を検査する。証拠文を書くだけで内容が真になるわけではなく、科学的正しさを自動認定しない。手順自体の妥当性は、故意の破損試験、見逃し事例、期限超過数、1回の点検量を記録して評価する。3回の実運用後に周期・粒度を見直すが、それまでも見逃しが出れば再設計する。

**この部分の結論：**未来SHAの循環なしに次回の開始点を残す。

#### S10-3から具体化した契約

変更完了の条件に、対象本文・コードだけでなく、構造索引、理論との対応、利用者向けの説明、対応テスト、版・確認範囲の更新を含める。書式と検査の実装はT-007で整備する。構造検査が通ったことを意味の完全性の証明にしない。規則の追加・検査の追加自体も、旧版の比較と回帰の対象である。

**判断をリポジトリへ戻す最小単位：**問いと要求ID、比較した選択肢、用いた証拠と時点、採否と判断者、採用/不採用の理由、代償・適用範囲、再検討条件をDECISIONSへ記録する。現在方針はCONTEXT、未確定はUNCERTAINTIES、次作業と受入はBACKLOG、実施はHTML、確認範囲・結果はHEALTH/REFERENCE_LOGへ結ぶ。同じ進捗全文を複数の正本へ複写せず、会話中の決定を未記録のまま終了しない。科学的根拠や数値を取得していない場合は、その不足と依存する判断を残す。

### DC-CHANGE — 方向転換時は、過去版を実際に比較する

<a id="DC-CHANGE"></a>
意味を変えた単位には、変更・理由・維持した情報・比較元の固定SHA・旧/新単位の指紋を`changes`へ記録する。全文の過去コピーは置かず、現在の判断に効く要約だけを残す。初回登録はinventory baselineと明示し、存在しなかった細粒度履歴を後付けで捏造しない。

**必ず過去本文を取得する契機：** 結論・仮定・適用範囲・単位の親を変える、説明を別資料へ移す、節を削除する、情報量を大きく減らす、要求と説明が食い違う、ユーザーが破壊的編集を指摘する場合。変更対象の現在本文と、前回受入版または変更理由が記録された版の同じ範囲を固定SHAで取得する。差分の行数だけでなく失う主張・導出・例・根拠を比較する。

元のSHAとパスが既知ならGitHub連携fetch_fileで取得する。ローカルの履歴を使う場合もコミットと実体を確認し、現在の作業ファイルを古いものへcheckoutしない。取得不可なら比較未了として該当変更の受入を止め、記憶で埋めない。

`python tools/check_contract.py . --base <変更前一式>`は登録済み論証単位の変更に対応する理由・旧新指紋を検査する。これも理由の妥当性を証明しない。移動・削除時は代替先と失われない情報をレビューする。初回の本版ではM082の本文を基準に再配置し、旧14契約の内容を保持した。新設の台帳に以前から細粒度履歴があったとはしない。

#### DC-STABILITY：一時点の健全性と、版をまたぐ安定性を分ける

<a id="DC-STABILITY"></a>
**問い：**健全な現行版から更新した結果が、別の形で健全に見えるだけで、意図・責務・使い方を徐々に失っていないか。FB-012は「現在の構造が健全であるだけでなく，その構造自体が版を経ても安定であるような性質」を要求した。安定とは同じ文字列・配置への凍結ではなく、通常の変更を局所化し、必要な構造変更を理由と移行先に結ぶことである。

**通常更新で保つもの：**同じ責務のパス、論証単位ID、親子関係、編集元の一意性、既存の受入証拠、読取入口、検査の安全境界。進捗や確認日だけの変更では、これらを作り直さない。構造の追加・移動・統合・分割・退役は、既存役割では足りない理由、比較した固定版、失われる情報の受入先、依存先への影響、失敗時の再開方法をそろえた例外として行う。単なる改版や文体上の好みを再編理由にしない。

**局所性：**葉の説明だけを変えたとき、親が含む全文のハッシュも変わる。しかし、それは親自身の論旨を書き換えた証拠ではない。論証の直下の子をID付き境界に置き換えた自身の指紋を用い、`changed_narrative_units`と`ancestor_impact_review`を分ける。親への影響の検討は省略しない。子の結論が変われば親の結論も点検し、必要なら実際に改訂する。順序・親・出力先を変えた場合は構造変更として検出する。

**遷移の検査：**`check_contract.py --base`は、用途・寿命、外部証拠の保管、資料設計、論証の入出力、点検範囲と依存、タスク前提・受入条件、復旧・期限・操作規則、検査器と回帰試験を、前後の実体から比較する。`structural_changes`に変更ごとの固定比較元・前後指紋・理由・維持した情報・影響・復旧を記録する。削除には明示的な受入先または役割終了理由を要する。比較元の全宣言パス/バイト集合を`comparison_base_sha256`へ結び、別版の展開フォルダーを誤用した比較を拒否する。この指紋はGitの認証ではないため、先にGitHubのコミット/treeとの同一性を確認する。

**検査規則自身の変更：**新しい検査器を弱めてから「全成功」とすることを防ぐため、原則として固定した変更前の検査器から候補を検査する。候補側だけの成功を証拠にしない。0.9.1はこの遷移検査の初導入であり、M090の旧検査器では新しい条件を保証できない。初回は旧検査の保存、差分の直接レビュー、旧版での見逃し再現、新版の正常・異常試験を組にする。以後は旧版の検査器で規則・ガードの変更を検出し、後方互換でないschema変更では停止して移行を別に審査する。確認記録の存在は人の承認や意味の正しさを自動証明しない。すべてのコードを編集できる主体への完全な改竄耐性はない。

**負荷と区切り：**変更したファイル数・追加削除パス・保持ID・自身の変更数と親の影響数を記録する。登録順序だけの変更、確認印だけの更新、同じ変換の再適用で構造が変わらないこと、少なくとも代表的な連続更新で同じ責務とIDを保てることを試験する。管理データの増大を理由なく許容せず、新しいルールは既存の責務内で表現できないか先に検討する。自動合格を得るために毎版全体を再分類することも、新しい管理層を際限なく追加することも避ける。閾値は根拠なく固定せず、実測コストと見逃しで見直す。今回の有限な反例修正と比較経路の保存を区切りとし、将来の全更新に対する数学的な安定性証明とは呼ばない。

**遷移要求の失敗時：** --transition は比較を実行できたことを要求する。基準の引数があるだけでは不十分で、フォルダーの実在、全宣言パス、旧contract、基準内容の一致を確認する。古い登録前状態の棚卸しと現行の前後遷移を混ぜない。表示だけのオプションと検査要求を同時に指定した場合も停止する。

**変更保護の範囲：** checker/testsだけでなく、prepare_workspace・run_checks・build_docsもガード対象とする。同期の保全条件・終了時照合・生成失敗の扱いを変えるコードは、単なる説明変更と区別して理由と影響を比較する。0.9.2のこの規則の整理時には、これらのツールのコード自体は変更していない。0.11.0での同期保全・比較検査の変更理由と反例はREFERENCE_LOGのAUD-110に記録する。新条件を持たない旧版での比較成功を、新条件の検証と呼ばない。

**この枝の結論：**意味ある変更には理由と比較対象を結ぶ。読取コストを減らすための要約と、必要な説明を消す編集を区別してから公開する。

### DC-PROCEDURE — 操作粒度を下げない

<a id="DC-PROCEDURE"></a>

**問い：**操作手順の省略をどう防ぐか。**根拠：**省略は操作の分散と誤りを招く。

操作の具体化にもDC-JUDGMENTを適用する。なぜその操作が必要かを目的へ結び、実施中の発見が目的や案と矛盾したら前段へ戻る。5欄が揃うことは、操作の選択や全体の流れが妥当であることの代わりにならない。

[更新:0.6.0] [確認:0.6.0]

S08-1と保存操作U02-1〜3、S09-1a〜c/2/3は、各操作に「前提、実際の操作、期待結果、停止条件、記録」を持たせる。操作欄を「前と同様」「U01参照」だけで済ませない。安全上の共通規則への参照は残せるが、どのrepo/branch/path、どの画面、どの値、どのボタン、どこまで変えるかは本文で確定する。

RPT-018で再発したため、操作5欄は存在だけでなく「今、誰が、何を入力し、どの一操作を実行し、何を次へ渡すか」が分かるかを読む。ユーザー向け画面操作とCodexの代行操作は担当を明示する。必要な保存を「後で具体化する」とだけ残さず、対象ブランチ・変更集合・実値の取得方法・実施記録欄を先に置く。自動実行前も同じであり、会話で実行してから記録先を探さない。

実施後は当初の指示を当時のものとして保持し、実施者・時点・入力/出力の実値・証拠・失敗/未済・再開位置を同じ手順へ追記する。指示の完了と次の実質作業を接続し、採用判断待ちと独立に進められる調査・設計を区別する。自己SHAの追記だけを理由とする無限保存は要求しない。

RPT-026/027：議論を必要とする手順では、操作内容を先に確定できなくても、人間に何を判断・提供してほしいか、根拠と代償、回答後の担当成果を明記する。議題名の一覧だけで回答待ちにしない。技術調査と一般の実装判断はCodexが進め、既決事項を再質問しない。拡張可能性の設計と科学的精度の検証を混同し、不要な先行試験を作業条件にしない。

**この部分の結論：**過去手順を探さず安全な一経路を再現できる。

### DC-ENV — DC-ENV：環境の観測と変更を分離する

<a id="DC-ENV"></a>

**問い：**環境の観測を採用とどう区別するか。**根拠：**存在する実行ファイルと成功条件は異なる。

S10の報告済み環境情報はユーザー実行/申告として記録する。パスの発見をツールの実行検証に、clone済みをHEAD/作業状態の確認に、容量割当を実空き容量に拡張しない。CLI採用時はCMD-ID・目的・実行場所・入力/出力・副作用・停止/再開・確認版を維持する。読取診断原文はHTML S10-2a、最小実行の実測原文はF01で、BUILDや会話はそこを参照する。

既存環境を壊さないため、最初の診断には導入/更新/設定変更/再clone/同期を混ぜない。出力が前提と違ったら観測してから次の具体手順を作る。PowerShell全体やユーザーPCで未実行のコードを「Windows検証済み」と呼ばない。

Codexの隔離実行で一時フォルダー等の権限により試験準備が失敗した場合、製品コードの失敗と分けて原出力を保存する。許可された同一検査を別の実行境界で再試験したときは、実行環境・隔離範囲・結果を別記録にする。試験成功のために安全検査やOS全体の設定を変更しない。

v0.7で3版周期へ到達する完了済み手順のレビューは、現在へ効く過去記録/再実行不要/後継手順との整合を対象とした。旧GitHub画面操作を再実行したり、現在UIの全面的な再保証を付けたりすることではない。旧S08冒頭の「未着手で止まっています」という残存時制は合格実績に合わせて修正した。周期と粒度の試行値自体は変更していない。

### DC-TEST-IO — DC-TEST-IO：テスト入力と出力記録を独立に管理する

<a id="DC-TEST-IO"></a>

**問い：**失敗時に何を証拠として残すか。**根拠：**端末表示は完全な記録と限らない。

本文の一部分だけを変える試験は、保存時に意図しないencoding/EOL変化を混ぜない。UTF-8とLFを明示し、EOL異常を試す場合は別試験で明示注入する。模擬プラットフォーム試験と実OSの成功は分けて記録する。

**この部分の結論：**失敗とファイル保全を別々に判定できる。

**問い：**呼出側の誤りをどう捕まえるか。**根拠：**関数試験だけではコピー原文の誤りを見落とす。
